## 背景・動機

W39 の発信運用振り返りの後、「H1〜H5 の仮説をある程度検証するのに必要なこと」を棚卸ししたところ、2つの仮説がデータ収集の構造問題で進められないことが分かった。

- **H4（W001 は翌日以降もインプを引く尾がある）**: 元の検証設計は「長文翌日の0本日インプ」比較だが、0本日ゼロが遵守目標になった今、意図的に0本日を作る検証は運用方針と矛盾する。X投稿一覧のインプ列は毎日更新されるが累積値しか残らないため、日次の伸び（尾）を後から復元できない。
- **H5（500字帯 vs 650字帯）**: 判定条件に「CTR 同等以上」が入っているのに、リンククリック列の更新は月次CSV（よーんの手動エクスポート→Drive アップ→update-x-analytics 手動実行）でしか回っておらず、直近投稿の CTR が常に欠落する。

また **H2（折り返しを「未回収の謎」で畳むと伸びる）** は、非適用側の同時期データが不足で保留が続いていたが、過去投稿の本文が X投稿一覧に残っているため、新規投稿ゼロの遡及分析で判定可能だった。

## 実施内容

### 1. H2 遡及分析 → 支持で確定

半減後（7/3以降）の W001 全12本について、ベースライン正規化倍率（IMP ÷ 直前の非W001・非リプライ5本の中央値）を再計算し、`x_fold_split.py` で折り返し位置を割り出して「畳まれる側の冒頭が種明かし・答えになっているか」で機械分類した。

- 種明かし直前群（n=5）中央値 **15.7倍** vs それ以外（n=7）中央値 **3.2倍**。境界例（8/15）をどちらに分類しても逆転しない
- Mann-Whitney 片側 p≈0.10。n=12 の事後分類につき、よーんの判断でこの水準をもって**支持・確定**とした（W39 レポート ⑦ に移動）
- 留保: B群最大の 7/3（167倍）が示すとおり、桁を決める主因はフックの謎の強さで、折り返し設計は増幅装置。制作標準としては `projects/w001/spec.md` 5.5／6.4・`brand.md` 採点基準 項目8 に既に同設計が入っており、ルール変更は不要（データの裏付けが取れたという位置づけ）

### 2. H4 用: W001 日次IMPスナップショット（`w001_imp_snapshot.py`）

- outputs シートから W001 の X 投稿を特定し、投稿9日以内のものの累積IMPを `logs/w001_imp_daily.csv` に「記録日, tweet_id, 投稿日, 累積IMP」で追記する。同じ（記録日, tweet_id）は追記しない（再実行しても安全）
- reporter-daily の STEP 10.5 として毎日 21:00 JST の日報 routine に組み込み、CSV は日報と一緒に commit される
- H4 判定は、投稿2日目以降の日次増分（尾）を W001 が4〜6本たまった時点で比較する

### 3. H5 用: X アナリティクス週次取込（`update_x_analytics_weekly.py` ＋ routine）

- Drive の Xanalytics/tmp の最新 CSV を鮮度チェック（既定7日以内）し、ダウンロード・パースして X投稿一覧の AA:AC（詳細表示・リンククリック・フォロー増）を1回の update で一括更新する。マッチしない行の既存値は保持
- exit code: 0=更新完了 / 2=新しい CSV なし / 1=エラー
- routine「**Xアナリティクス週次取込（リンククリック更新）**」（`trig_01HFX4MQShcvrr6dpWw5J7ty`・毎週日曜 18:17 JST・fresh session・Gmail＋Drive コネクタ）を新設。exit 2 ならリマインドメール、exit 1 ならエラーメールを useakat@gmail.com に送る。日曜 20:00 の reporter-weekly-ops が最新 CTR を使える順序にした
- よーんに残る手作業は週1回の「X アナリティクス → コンテンツ からエクスポート → Drive アップ」のみ（X API が有料のため自動化不可）

## 設計判断

- **スナップショットの置き場を update-x-analytics ではなく日報 routine にした**: update-x-analytics は月次CSV起点で日次データが取れない。毎日走る既存 routine への相乗りが最小コストで確実
- **週次取込の書き込みを「AA2:AC最終行の全体ブロック書き戻し」にした**: 散在するマッチ行を個別 update すると API 呼び出しが数十回になる。既存値を読んでマッチ分だけ上書きした全体ブロックを1回で書く方式なら get 2回＋update 1回で済み、マッチしない行も壊さない
- **リマインドはメールのみ・成功時は無通知**: 成功はレポートの CTR 反映で分かるため通知しない（monthly リマインド routine の設計を踏襲）
