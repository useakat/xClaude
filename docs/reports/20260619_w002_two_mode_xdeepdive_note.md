## 背景・動機

w001 で作成した X長文ポスト（例：「ボイジャー再点火」）のテーマを、より深掘りした
6000〜8000字・980円の有料 note 記事にしたいという要望があった。

しかし現行の `w002/spec.md` は **ネタ起点（`noteNeta` シートの未使用ネタから新規 notebook を
作って書く）** の単一フローしか想定しておらず、「既存 X長文ポストを入力源にして note にする」
経路が存在しなかった。

調査の結果、提案フローは現行フローと **導入部（題材確定〜構成承認まで）だけが異なり、
本文執筆以降のパイプライン（本文→チェック→ファクト→参考情報→画像→サムネ→ハッシュタグ→
ネタ更新→メール）は完全に共通** であることが分かった。そこで新規 spec を作らず、
1つの spec.md に2つの導入部を持たせて本文以降で合流させる構成に改修した。
これは先行して W001 側（X長文制作）を2モード化した変更と対になる。

## 実施内容

- 制作フロー冒頭に **モード判定** を追加。
  - **モードA（ネタ起点・新規）**: 従来フロー（`noteNeta` 未使用ネタ→新規 notebook）。
  - **モードB（X深掘り）**: 既存 X長文ポスト（w001）を深掘りして有料 note にする新フロー。
- 導入ステップを A1–A5 / B1–B7 に分け、ステップ6以降を「共通フロー」として合流。
- モードB の特徴:
  - notebook は w001 のものを **再利用＋必要時のみソース追加**（新規作成しない）。
  - ネタ番号の確認はしない（`neta-id.md` を読まない）。
  - 記事フォルダの `<短いタイトル>` は元 X長文ポストフォルダ名（日付以降）と同じにする。
  - `source-x-post.md` に元フォルダの相対パスを記録（`sync-x-note-analytics` の導線集計用）。
  - 構成案5案（NotebookLM に X本文＋方針を同梱して問い合わせ）→ タイトル5案 → 文字配分込み構成、の3段階対話で承認を取る。
  - ネタ使用済み更新は行わない。
- 共通フローの調整:
  - 文字数目標を「6000字以上」→「**6000〜8000字**（有料980円想定）」に band 化。
  - ステップ9のファクトチェックを `/check-fact` → `/check-fact-lim <notebook_id>`（notebook ソース限定）に変更。
- ついで修正: `draft/agenda.md`・`draft/draft.md` の未閉じバッククォート、`/check-fact``` の余分なバッククォートを解消。

## 設計判断

- **新規 spec を作らず1ファイル2モードに統合**: 本文以降が完全共通のため、別 spec にすると
  保守対象が二重化し、共通部の変更漏れが起きやすい。導入部だけ分岐して合流させる方が DRY。
- **モードB の対話は3段階（構成→タイトル→文字配分）**: 深掘り題材は選択肢が広く、構成（切り口）の
  決定が最大の分岐点。先に構成を確定してから命名・配分に進む方がユーザーの制御が効くため、
  モードA の一括提示（タイトル10案＋構成＋配分を1回承認）とは別建てにした。
- **notebook は再利用＋必要時追加**: w001 でテーマ向けソースが既に curate 済み。note は X より
  深いが、まず再利用し、本文で事実が不足する場合のみ既存のリサーチ運用ルール（重複確認のうえ）で追加する。

## 確認結果

- 改修後の `spec.md` を通読し、モード判定 → モードB導入（B1–B7）→ 共通フロー（6–15）が
  一本道で読めること、モードA導入（A1–A5）が従来どおり成立することを確認。
- 承認済みの4点（B2ネタ確認削除・短いタイトルはX投稿フォルダ名踏襲・`/check-fact-lim`・モードBはネタ更新なし）が反映されていることを確認。
