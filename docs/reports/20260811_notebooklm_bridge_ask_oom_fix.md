## 背景・動機

SOHO 復活劇の販促投稿（w002）制作中、check-fact-lim 相当の裏取りとして `notebooklm_browser_bridge.py ask` に5問まとめの質問を渡したところ、数分〜十数分経っても応答が返らない・空応答になる不具合が発生した。ユーザーから「なんでブリッジ経由の ask が機能していないのか、調べて」と調査依頼があった。

段階的に切り分けた結果、原因は以下と判明した：

- ブリッジ自体（`list`・`list-sources`）は正常動作
- 質問の長さは無関係（1175文字の単純な質問は28秒で成功）
- 詳細な単問は成功するが、複数問まとめると失敗する
- `dmesg` に OOM Killer によるローカル `python3` プロセスの強制終了が2件記録されていた（`anon-rss:864684kB`・`anon-rss:849164kB`）

チャットのストリーム応答（`GenerateFreeFormStreamed`）は、更新のたびに「その時点までの回答全文＋引用メタ全部」のスナップショットを送り直す形式で、更新回数分（実測74回）だけ同じ数百KBの引用メタが重複して送られていた。実測で、詳細な単問1件でも生応答が24MB〜32MBに達し、ローカル側の JSON 展開・パースで RSS が 391〜518MB まで膨らんでいた。5問まとめでは生応答が59MBに達し、850MBを超えて OOM Killer に殺されていた。

エラーが無言の SIGKILL で起きるため、呼び出し側からは「ハング」または「空応答」にしか見えなかった。

## 実施内容

- Windows 側にしか存在しなかった `nbrpc_server.py`（ブラウザ内で fetch を実行する常駐サーバ）をリポジトリに取り込み、`scripts/nbrpc_server.py` として正本化した
- チャット応答（`GenerateFreeFormStreamed`）のときだけ、**ブラウザ内**で末尾2つの `wrb.fr` チャンク（＝最新の完成版スナップショット）だけを残し、それ以外の `wrb.fr` チャンクを間引くトリム処理を追加した
  - `wrb.fr` 以外の小さいチャンク（`di`・`e`・`af.httprm` 等）は保持
  - `UserDisplayableError` を含むチャンク（レート制限エラー検出用）は無条件で保持
  - 想定外の応答形（`wrb.fr` が1つも無い等）や例外時は無加工でそのまま返すフォールバックを入れた
- node でトリム JS 単体のユニットテストを作成し、trim動作／エラーチャンク保持／非チャットは無加工／構造異常時は無加工／出力構造の妥当性の5項目を確認した
- デプロイ手順（`scp` ＋ SHA256 ハッシュ照合）を `nbrpc_server.py` の docstring に記載した

## 設計判断

- **ブラウザ内で捨てる**：ローカル側でトリムを試したところ RSS が逆に518MBへ増加した（32MBの文字列を ssh 経由で受け取り `json.loads` した後では手遅れ）。文字列がもともと存在するブラウザ内（Chrome の JS 実行コンテキスト）で捨てることで、ssh を渡るデータ量そのものを削減した。
- **末尾2チャンクを残す**：各チャンクは完全なスナップショットであり、パーサは「最も長い marked answer」を採用する実装のため、最後の（＝最も長い）ものを残せば従来と同じ結果になる。実測で回答・references とも完全一致を確認した。
- **`notebooklm_browser_bridge.py`（ローカル側パーサ）は無変更**：vendor 実装（`vendor/notebooklm/_chat.py`）を変更せず、Windows 側のトリムだけで解決した。パーサ側の変更はライブラリの reverse-engineered 実装への手入れになり保守コストが高いため避けた。

## 確認結果

- 詳細な単問（Q1）：生応答 24,024,129文字 → 受信 984,384文字（24分の1）、ピーク RSS 391MB → 47MB、39秒で完答（回答1,782文字・references 44件、内容一致確認済み）
- 修正前に OOM で死んでいた5問まとめの質問：生応答 59,288,752文字 → 受信 906,903文字（65分の1）、75.9秒で5問すべてに完答（末尾まで途切れなし）
- `list`（133件）・`list-sources`（62件）が従来どおり動作することを確認し、非チャット系エンドポイントへの影響が無いことを確認した

## 今後の課題
