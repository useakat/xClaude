## 背景・動機

よーんから「予約を削除しても、投稿が登録されたままになっている」という指摘があった。

原因は取り込み処理（`scripts/postcal_import.py`・10 分ごと）にあった。予約ファイル（`outputs/scheduled-posts/**/*.md`）から取り込んだ予約を画面で削除しても、予約ファイルはリポジトリに残る。取り込み処理は「取り込んだはずの予約が DB に無い」ことを見つけると、新規として作り直していた。そのため、削除から 10 分以内に同じ内容の下書きが別の番号で復活していた。

取り込みログと DB を突き合わせると、次の 4 件がこの経路で復活していた（かっこ内は削除された元の番号）。

- #32 アポロ12号 落雷と管制官（#18・#22・#29）
- #30 クラゲ銀河（#24）
- #31 系外銀河 塵の奥のベンゼン（#25）
- #27 神舟5号 ポゴ振動（#26）

復活するのは下書きなので、「投稿予約」を押さないかぎり投稿はされない。ただ、消したものが戻ってくるので、カレンダーを整理できなかった。

## 実施内容

よーんが選んだ 2 段階の方式で実装した。

1. 画面で「削除」を押した時点で、postcal がその予約を「削除済み」と記録する。この時点で、取り込みによる復活は止まる
2. 10 分ごとの取り込み処理が、削除済みの予約の予約ファイルを消して master に commit・push する

- postcal.db に、削除済みを記録するテーブル `deleted_posts`（`post_id`・`deleted_at`）を追加した。`db.delete()` が、予約の削除と同じトランザクションで記録する
- 取り込み処理は、削除済みの予約の予約ファイルを見つけたら再登録せず、`git rm` → 対象パスだけを commit → `git push origin HEAD:master` を行う。コミット名は「postcal: 画面で削除した予約のファイルを削除（N 件）」
- 消せたら、その uid を取込状態（`import_state.json`）から外す。同じ uid の予約ファイルがあとで作り直された場合は、新規として登録される
- push できなかったときは、自分のコミットを取り消してファイルを元に戻し、次回の実行でやり直す。3 回（30 分）続いたらメールで知らせ、その後は 1 日 1 回知らせる。その間も下書きは復活しない
- `--dry-run` では、削除予定をログに出すだけで何も変えない
- `docs/workflows/x-auto-post.md` に、この動きを 1 項目追記した

## 変更ファイル

| ファイル | 変更内容 |
|---|---|
| `postcal/db.py` | テーブル `deleted_posts` を追加。`delete()` が削除済みを同時に記録する。`deleted_ids()` を追加 |
| `scripts/postcal_import.py` | `upsert()` が削除済みの予約を `deleted` として返す。`remove_reservation_files()`（git rm・commit・push・失敗時の巻き戻し）と `_git()` を追加。`main()` に削除・通知・取込状態の整理を追加 |
| `docs/workflows/x-auto-post.md` | 画面で削除した予約の予約ファイルの扱いを追記 |

`postcal/app.py` は変えていない。削除ボタンの処理が呼ぶ `db.delete()` の中で記録するため。

## 設計判断

- **予約ファイルを消すのは、画面の削除処理ではなく取り込み処理にした**。VPS 上でファイルだけ消すと未コミットの削除が残り、上流でそのファイルが更新されたときに `git pull --ff-only` が通らなくなる。Web のリクエストの中で push するのは、失敗したときの扱いが難しい。取り込み処理はもともと git を扱い、失敗をメールで知らせる仕組みを持っているので、そこに載せた
- **「取り込んだら予約ファイルを消す」案は採らなかった**。予約ファイルを同じ uid で上書きして改稿する運用（直近で 8 回）が使えなくなり、`/writer-xpromo` が未投稿の販促を避けるために `outputs/scheduled-posts/w007/*.md` を読む処理も効かなくなるため
- **削除済みの記録は postcal.db のテーブルに置いた**。取込状態のファイルは取り込み処理が毎回書き直すので、画面側から書くと競合する
- **「DB に無い」だけでは予約ファイルを消さない**。消すのは削除済みの記録がある予約だけにした。記録が無いのに DB に無い場合（DB を作り直したときなど）は、従来どおり予約ファイルから作り直す。DB を失ったときに予約ファイルまで全部消えるのを防ぐため
- **削除のあとに予約ファイルが書き換えられていた場合は、消さずに新しい下書きとして登録する**（よーんの承認文には無い、実装側の判断）。削除直後に依頼した改稿が黙って消えるより、下書きとして見えるほうが気づける。不要ならもう一度削除すれば、今度はファイルも消える
- **ローカルの master が origin/master と一致しているときだけ消す**。VPS のリポジトリでは他のセッションも作業する。その未 push のコミットを一緒に push しないため。一致していない間は見送り、次回やり直す
- **対象のパスだけを commit する**。作業ツリーの他の変更・ステージ済みの変更は含めない。未コミットの変更がある予約ファイルと、git 管理外の予約ファイルは消さない
- **systemd から動くときは `HOME` が無い**ので、`_git()` で補っている。補わないと `~/.gitconfig` が読まれず、コミットの名義が決まらない
- **投稿済みの予約のファイルは消さない**。追加案として挙げたが、よーんの返事が無かったので入れていない

## 確認結果

本番と切り離した試験用リポジトリ（bare のリモート＋クローン。メール送信は代役のスクリプト）で通し試験を行い、すべて合格した。

- 画面の削除（Starlette TestClient で `/posts/{id}/delete`）のあと、下書きが復活せず、予約ファイルがローカルと origin/master の両方から消える
- コミットに入るのは対象の予約ファイル 1 件だけで、他のステージ済み・未ステージの変更は残る
- push 失敗時はファイルと HEAD が元に戻る。3 回続くと通知が 1 通出る。復旧後の実行で消える
- ローカルに未 push のコミットがある間は見送り、それを push していない。push 済みになれば次回で消える
- 削除のあとに改稿された予約ファイルは残り、新しい下書きになる。それをもう一度削除するとファイルも消える
- 削除の記録が無いのに DB から消えた予約は、従来どおり作り直される
- 同じ uid の予約ファイルを作り直すと、新規として登録される
- 投稿済みの予約の削除は従来どおり 409。`--dry-run` ではファイルもコミットも変わらない

本番では、`postcal.service` を再起動して `/healthz` が 200、`--dry-run` で従来どおりの集計（locked=12 / skip=7）になることを確認した。本番での実際の削除（予約ファイルの削除と push）は、この報告書を書いた時点ではまだ一度も行われていない。X / Threads への投稿は行っていない。

## 今後の課題

- 復活している下書き 4 件（#32・#30・#31・#27）は、よーんが画面でもう一度削除する。次の取り込みで予約ファイルも消える。これが本番での最初の動作確認になる
- 取り込み処理が master に自動でコミットするようになった。VPS から定期的に自動コミットする処理はこれが初めてなので、最初の数回はコミットの内容を見ておく
- 画面の削除完了メッセージは「削除しました（#id）」のままで、予約ファイルもあとで消えることは表示していない
