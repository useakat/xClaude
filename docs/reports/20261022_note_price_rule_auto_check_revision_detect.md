## 背景・動機

同日に決めた「note 記事の価格設定ルール」（¥100 開始 → 200 PV で 2 部以上なら上げる → 1 部以下なら冒頭と有料ラインを見直して次の 200 PV を待つ → 上げた価格の 売上/1,000 PV が前を下回ったら戻すかブラッシュアップするか判断）は、人が「200 PV に達したか」を見に行かないと動かない。よーんから「規則に則った改善作業を忘れずにできるようにしたい」と相談があり、条件を満たした瞬間に知らせる仕組みを毎朝の cron に組み込んだ。

規則 3 の「見直し後、さらに 200 PV」を数えるには改稿日が要る。最初はよーんがシートに手で入れる案を出したが、手入力は忘れるので、note の公開 API から取れる本文で自動検知することにした。有料記事の API は無料部分までしか返さないため、題名 ＋ 無料部分 ＋ 有料部分の文字数・画像数をハッシュにして比べる。よーんの要望で、自動記録したときは必ず通知する。

## 実施内容

- `note価格履歴` に **本文ハッシュ・改稿日・通知日・通知内容** の 4 列を追加（見出しは `_ensure_hist_header` が自動で補う）
- `fetch_note`：公開 API から価格と本文ハッシュを取る（`fetch_price` はその薄い包み）。`update_prices` が全記事のハッシュを集めて返し、価格変更で新しい区間を足すときにハッシュを入れる（価格変更を改稿と誤認しない）
- `check_price_rule`：開いている区間（現在価格・有料）ごとに
  - ハッシュが空なら控えるだけ（初回・通知なし）。前回と違えば **改稿日 ＝ 今日** を記録し、通知内容を空にして「改稿を検知」を通知。PV と購入は改稿日から数え直す
  - 区間（改稿日があればそこから）の PV を `note記事日次`、購入を `note購入記録`（題名 → 記事ID、価格一致、±1 日）から数え、200 PV に達したら 規則 4 → 2 → 3 の順で動作を決める。規則 4 は直前の区間（価格が低いもの）の 売上/1,000 PV と比べる
  - 同じ動作は通知済みなら送らない（「通知内容」の規則番号で比較）。新しい動作は 通知日・通知内容 を書いてメール
- メールは `send_gmail.sh` で `useakat@gmail.com` へ、件名【note価格】N 件の動作、本文に記事・価格・PV・購入・売上/1,000 PV・動作と規則の要約
- 照合やメールに失敗しても日次 PV の記録は止めない。`--dry-run` は通知本文を出して送らない。`--prices-only`・取得対象なし・通常実行のどの経路でも照合する
- レジストリの価格設定ルールの節に「運用（自動）」、`docs/scripts/index.md` の行を更新

## 設計判断

- **改稿日は自動検知**：手入力は忘れる。API の本文は有料記事では無料部分までだが、規則が求める「冒頭と有料ライン」の改稿は無料部分の末尾が変わるので検知できる。有料部分だけの修正は検知できず、誤字修正も改稿になる（その場合はよーんが改稿日を消す）
- **通知は 1 回だけ**：毎朝同じ内容が届くと読まれなくなる。規則番号が変わったとき、改稿で数え直しが始まって再び 200 PV に達したとき、価格が変わって区間が新しくなったときに改めて通知する
- **規則 4 を先に見る**：上げた価格で 2 部以上売れていても、売上/1,000 PV が前の価格に負けていれば「上げる」ではなく判断の対象にする
- **既存の cron に相乗り**：日別 PV・価格・購入のデータが同じ実行の中にそろっているので、別の routine を作らない

## 確認結果

- `py_compile` 通過。`--prices-only --dry-run`：ボイジャー再点火の価格変更（¥980 → ¥590、よーんが当日変更）を検知。旧 ¥980 区間（388 PV・0 部）は規則 4「戻すかブラッシュアップするか判断（売上/1,000 PV 0 円 ＜ ¥490 の 3,508 円）」、赤い空（後編）¥490（233 PV・4 部、8,412 円 / 1,000 PV）は規則 2「価格を上げる」と判定。ニューホライズンズ ¥300 は 187 PV で未達（通知なし）
- 本番の初回は 10/23 05:55 の cron。よーんは「今すぐ実行」を選ばなかったので cron に任せる。初回は全記事のハッシュを控え、ボイジャーの ¥590 区間を立て、赤い空（後編）の通知メールが 1 通届く見込み
