## 背景・動機

note 導線（X / Threads → note 到達 → 購入）の計測は 10/4 の転送サイト、10/11 のダッシュボード、10/18 の週次ファネル整理で揃ったが、「何を直すか」の改善策は 7 月のマネタイズ月報、各報告書の今後の課題、10/8 の発信軸改定などに散らばっていて、順序も検証方法も決まっていなかった。W42 の運用振り返りで「note 記事の公開は当面保留、導線の整備を優先」と決めたので、改善策を 1 か所に順位付きで置き、施策ごとに判定条件を実施前に固定し、週次で結果を積めるようにした。

実装の途中で 2 つの問題が見つかった。

1. **CVR が価格をまたいで混ざっていた。** 有料記事の CVR（購入 ÷ PV）は記事間で 5 倍の開きがあるが、同じ記事でも価格が何度も変わっている（ニューホライズンズ ¥100→¥200→¥300、天王星 ¥100→¥200→¥290→¥390、ボイジャー再点火 ¥490→¥980、チャンドラセカール ¥100→¥200）。累計 PV ÷ 累計購入では価格の違う期間が混ざり、値段の効果も記事の効果も読めない。よーんの指示で、CVR は価格を明示した「CVR¥300」の形にし、記事ごと・価格ごとに計算できるようにした。
2. **`note記事日次` の日別 PV に累計値が混入していた。** 10/17 のニューホライズンズが 2,600 PV（前後の日は 0〜2）になっていた原因を追うと、note の GraphQL はその日に動きの無かった記事を返さず、`fetch_note_stats.py` がその記事のビューを REST の累計で埋めていた。`note_article_daily.py` は警告行から除外対象を読んでいたが、警告には先頭 5 件しか載らないため、6 件目以降の累計値がそのまま日別に書かれていた。10/4 以降の全日に影響していた。

### 4. 記事 × 価格区間の CVR¥

- **`note価格履歴` シート**（発信記録に新設。記事ID, タイトル, 価格, 開始日, 終了日, 出典）。初期 36 行は `note_article_daily.py --init-price-history` が `note購入記録` の購入時価格と `note投稿一覧` の現在価格から推定して作った（価格が変わった最初の購入日を新区間の開始日にし、出典列に変更日の幅を書く）。以後は `note_article_daily.py` の毎朝の価格チェックで変更を検知し、開いている行を前日で閉じて新しい区間を足す
- **`article_price_cvr.csv`**（9 本目の CSV）：1 行 ＝ 記事 × 価格区間。PV ＝ 区間内の `note記事日次` 合計、購入数 ＝ `note購入記録` を日付と価格で区間に割り当て（変更日当日に新旧価格が混在するため ±1 日の幅で価格一致を優先）、CVR、販売係数、売上、PV取得日数（区間のうち日別 PV がある日数）、現在価格
- **`articles.csv`**：CVR と販売係数を現在価格の区間で計算し、累計（価格混在）は `CVR（累計・価格混在）` として別列に残した。`現価格PV` `現価格購入数` `現価格PV取得日数` `現価格開始日` を追加
- **ダッシュボード v29〜v30**：記事別の CVR を「¥300 0.53%」の価格付き表示に、新セクション「価格別 CVR」（表 ＋ 価格帯 100 円刻み × CVR¥ の散布図。1 点 ＝ 記事 × 価格期間、PV 300 未満は薄く、点の大きさは購入数）、散布図「100PV あたり」の横軸を現価格区間に、用語説明に CVR¥ を追加。datasets に `article_price_cvr` を追加し、routine「note 導線ダッシュボード更新」のプロンプトを 9 本の CSV に更新

### 5. 日別 PV の累計混入の修正とバックフィル

- `fetch_note_stats.py` の出力に `gql` フラグ（False ＝ その期間のダッシュボード値が無く view/like は REST 累計）を追加
- `note_article_daily.py` の `fetch_day` は `gql` が False の記事を 0 として書く（警告行の先頭 5 件だけを除外していた処理を廃止）。全件 False なら書き込まない
- `--from YYYY-MM-DD` と `--max-days N` を追加し、2026-02-22（最古の記事）〜 10/20 の全日を取り直し・遡って取得した。連続取得で note が非 JSON を返して拒否したため、日と日の間に 3 秒の間隔と、失敗時の再試行（30 / 90 / 180 秒待ち）を入れた

## 設計判断

- **レジストリは Markdown 1 ファイル**（よーん決定）。定義・検証方法・結果を同じ場所に置き、仮説管理で起きた「SKILL.md の定義と週次レポートの判定のずれ」を避ける
- **ヘルパーは数値だけ、判定は Claude**。判定条件は文章で書かれ、例外（混在週・データ不足）の扱いに判断が要るため
- **N1〜N3 の判定は「倍率 ＋ 母数の下限」の 2 条件**。X のプロフアクセスは週 15 件程度で、p 値を緩める（p<0.3 なら母数 15〜40 件で足りる）と週ごとの偶然で支持になる。4 週（約 60 件）を下限にして 1.5 倍以上で支持とし、p 値は添えるだけにする。検証を早めるには週のプロフ数を増やすしかない
- **N10 は記事をまたいだ価格帯比較をしない**。記事の差が混ざるため、同一記事の価格区間ごとに 売上/1,000 PV（CVR¥ × 価格）で比べる
- **価格履歴の境界は推定を許す**。変更日はどこにも残っていないので、購入記録から「変更は X〜Y の間」と幅付きで記録し、以後は API で確定させる

## 確認結果

- `--init-price-history --dry-run` で 36 行（有料 11 記事は価格区間に分割、無料は 1 区間）。書き込み後にシートを確認
- 全日取り直し後、`note記事日次` の日別合計が `note流入元` の日別合計と一致（9/28 が 76 と 76、10/4 が 89 と 89）。10/17 のニューホライズンズは 0
- `note_funnel_export.py`：`article_price_cvr.csv` でニューホライズンズが ¥100 / ¥200 / ¥300 の 3 行、購入数の合計 10 が `articles.csv` と一致。全区間の PV取得日数 ＝ 日数。価格不一致の警告なし
- `note_funnel_measures.py --all`：N6 が `CVR¥300 0.53%` 表記、N10 が同一記事の価格区間比較（ボイジャー ¥490 838 PV・6 件 → ¥980 388 PV・0 件 など）
- ダッシュボード v30：記事別の CVR 列、価格別 CVR 表、価格帯 × CVR¥ 散布図。スクリプトは node --check で構文確認
- Wiki のローカルビルドはメモリ不足で止められたため未確認（CI が push 後にビルド）

- チャンドラセカールの 9/28 Threads 投稿は手動投稿で発信記録に行が無く、投稿ごとのファネルに載っていない
- N1〜N3 は週のプロフアクセスが増えないと判定に 7 週以上かかる
