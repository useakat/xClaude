## 背景・動機

W001（X長文）のサムネイル生成は、これまで spec 上「Claude は `nanobanana-prompt.md` を提示するところまで担当し、**ユーザーが外部の画像生成AI で生成する**」という運用だった。リポジトリに生成ツールが無いことが前提だったためである。

しかし今回、よーんの指摘で **ユーザーレベルに lovart スキル（`~/.claude/skills/lovart/`）が導入済み**であり、API キー（`LOVART_ACCESS_KEY` / `LOVART_SECRET_KEY`）も設定済みで、**Claude が直接画像を生成できる**ことが判明した（日報 7/30・7/31 に「claude code から画像生成するのに lovart を使ってみてる」と記録あり）。当初 Claude が「アクセスできない」と誤答したのは、当該スキルがセッションのスキル一覧に出ていなかったための早合点だった。

これを機に、海王星 note 販促投稿のサムネ制作で lovart を初運用し、W001 の画像工程を「プロンプトを渡して終わり」から「**Claude が生成し、対話で詰める**」フローへ実質的に移行した。

## 実施内容

- **lovart スキルの利用手順を確立**：`config --json` で active_project 確認 → `upload --file` で参考画像を CDN へ → `chat --attachments <url> --json --download` で生成 → `--thread-id` を使い回して対話改稿。タイムアウト時は `result --thread-id` で成果物を回収できることも確認。
- **史実準拠を担保する参考画像の運用**：Wikimedia Commons から **海王星発見に実際に使われたフラウンホーファー9インチ屈折の現物写真（CC0）** と新ベルリン天文台の断面図（PD）を取得し、生成時に添付。これにより「木製鏡筒＋真鍮パーツ＋木製ドイツ式赤道儀」という正しい形式を指示でき、AI が描きがちな三脚式・反射式の誤りを回避した。
- **実在人物の扱いルールを design-brief に明文化**：チャリス・ガレ・ダレストは肖像が現存するため、**人物は全員「完全な黒シルエット・顔を一切描かない」**と規定。「似ていない」という破綻が原理的に起きない構成にした（AI が苦手な顔の破綻回避にもなる）。
- **対話改稿の実践**：初回生成 → 明るさ／望遠鏡の向き／2台の差別化／場所の分離 → 中央帯の強調・右端の閉塞 → 明暗の再調整 → 人物ポーズ変更、と 6 回の改稿を経て最終版を確定。バリエーション4案を `draft/candidates/` に保存して比較した。
- **画像の Drive-only 運用を jpg へ拡張**：参考画像（jpg）も git に載せないよう `.gitignore` に `/projects/w00{1,2,3}/**/*.jpg` を追加（7/30 の png 除外の延長）。

## 設計判断

- **参考画像を「最初から」用意する**：形式違い（三脚式・反射式）は天文に詳しい読者から即座に指摘される。プロンプトの文章指示だけでは AI が形式を外すため、実機写真の添付を標準手順とした。
- **人物はシルエット固定**：肖像が残る歴史上の人物を扱う W001 では、顔を描かない方針が事実面・品質面の両方で有利。今後の同種テーマにも適用できる。
- **spec の書き換えは今回見送り**：`spec.md` のステップ10は「外部で生成」のままとした。lovart の運用が数本の制作で安定したことを確認してから、正式にフローを書き換える。

## 確認結果

- lovart 経由で画像生成 → `output/thumbnail.png` 配置 → `【X長文】` Gmail 下書き（本文＋`[note_url]`＋`[リプ]`＋サムネ添付）作成 → Drive アップロードまで、W001 の全工程が完走した。
- design-brief のレビュー基準（サムネサイズでの左右対比／顔が写っていない／望遠鏡が据え付け大型屈折／文字なし）を最終版が満たすことを目視確認。
- `git status` で png・jpg いずれもステージされないことを確認（画像は Drive のみ）。

## 今後の課題

- lovart 運用が安定したら、`projects/w001/spec.md` のステップ10（および w002 の該当ステップ）を「Claude が lovart で生成する」フローに書き換える。
- 同一スレッドへの並列 `chat` 呼び出しは同じ成果物を返すため、バリエーション生成は逐次実行する必要がある（今回判明）。
