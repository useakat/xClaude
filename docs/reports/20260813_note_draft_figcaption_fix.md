## 背景・動機

オポチュニティ記事の下書きを `send_note_draft.py` で保存し、ユーザーが編集URLを開いたところ **404** になった。作り直しても同じ。note の下書き一覧には記事名が並ぶのに、クリックすると404という状態だった。

API で下書きのレコードを引くと、データ自体は完全だった。

| 項目 | 値 |
|---|---|
| status | `draft` |
| 所有者 | user_id 12292575（takaesu7431 本人） |
| 本文 | 31,466文字・`<figure>` 11個 |
| `note_draft` レコード | 本文・タイトル・format 4.1 とも格納済み |

エディタの URL は3形式とも同じ 37KB の空の SPA シェルを返す（記事の中身はブラウザ側から取りに行く作り）。つまり **404 はブラウザ内で出ており、サーバー側にデータが無いわけではない**と分かった。

なお [2026-08-10 の実装](./20260810_note_draft_images_eyecatch/) の「確認結果」はローカルの HTML 変換検証・`py_compile`・`--help` だけで、**実際に作った下書きをエディタで開く確認をしていなかった**。そのため、画像入りの下書きは一度も開けたことがないまま出荷されていた可能性が高い。

## 実施内容

原因の候補が多く（本文量・図・リンク・見出し・目次ブロック）、推測では詰められなかったため、**テスト下書きを作ってユーザーに開いてもらう切り分け**を3ラウンド行った。

### ラウンド1 — API 経由の下書き作成そのものを疑う

| # | 内容 | 結果 |
|---|---|---|
| 1 | 段落2つだけ | 開ける |
| 2 | 目次ブロックあり（`name` と `id` を一致） | 開ける |
| 3 | 目次ブロックあり（`name` ≠ `id`・当時の出力） | 開ける |

→ API 経由の作成は問題なし。`<table-of-contents>` の `name`/`id` 不一致（当時の疑い）も無関係と判明。

### ラウンド2 — 本文の要素を分解する

| # | 内容 | 結果 |
|---|---|---|
| 4 | 記事本文まるごと・画像記法だけ削除（28,034字） | 開ける |
| 5 | 短い本文＋**画像1点**（`<figure>` 1つ） | **404** |
| 6 | 参考情報23件（リンクのみ・壊れたURL含む） | 開ける |

→ 本文量でもリンクでもなく、**`<figure>` が原因**と確定。

### ラウンド3 — figure の属性を1つずつ足す

note 自身が書き出す画像ブロックと、こちらの生成物を比較して差分3点（`data-align` / `figcaption` / `alt`）を抽出し、1要素ずつ足したテストを作った。

| # | 条件 | 結果 |
|---|---|---|
| 7 | **figcaption あり**（data-align なし・alt 日本語） | 開ける |
| 8 | figcaption なし・data-align あり | **404** |
| 9 | figcaption なし・alt 空 | **404** |
| 10 | 3つとも（note 完全準拠） | 開ける |

→ **`<figcaption>` が無い `<figure>` をエディタが読み込めない。** `data-align` と `alt` は無関係。

### 修正した3点

```python
# ① figcaption（404の直接原因）。あわせて note 自身の出力に合わせ data-align も付ける
- f'<figure name="{uid}" id="{uid}">'
- f'<img src="{info["src"]}" alt="{alt}"{size}>'
- f"</figure>"
+ f'<figure name="{uid}" id="{uid}" data-align="center">'
+ f'<img src="{info["src"]}" alt="{alt}"{size}>'
+ f"<figcaption></figcaption></figure>"

# ② URL に括弧を含むリンクが壊れる（切り分け中に発見）
- r"\[([^\]]+)\]\(([^)]+)\)"
+ r"\[([^\]]+)\]\(((?:[^()\s]|\([^()\s]*\))+)\)"

# ③ HTML コメント行を本文に出力しない（同上）
+ if line.strip().startswith("<!--"): continue
```

②は `[Opportunity (rover) - Wikipedia](https://en.wikipedia.org/wiki/Opportunity_(rover))` が
`href="https://…/Opportunity_(rover"` で切れ、本文に `)` が漏れていた（参考情報の Wikipedia リンクが該当）。
③は `output/index.md` 末尾の `<!-- ハッシュタグ -->` が `<p>` の中に生で入っていた。

## 変更ファイル

| ファイル | 変更内容 |
|---|---|
| `scripts/send_note_draft.py` | figure に `<figcaption></figcaption>` と `data-align="center"` を追加（コメントで理由と検証日を明記）。Markdown リンクの正規表現を括弧1段のネスト対応に変更。HTML コメント行をスキップ |

## 設計判断

**推測で直さず、テスト下書きで1要素ずつ潰した。** 本文には画像・見出し・リンク・目次・31KBの本文と変数が多く、「たぶんこれ」で直すと外れたときに切り分けが振り出しに戻る。1ラウンドで複数の下書きを作り、ユーザーには「開けたかどうか」だけを答えてもらう形にして、3往復で原因を1点に絞った。

**figcaption は空のまま入れる。** 画像のキャプション（クレジット等）は本文側に段落として置く運用にしているため、figcaption に文字を入れると二重に表示される。エディタの文書モデルが要求する空タグとして置く。

**②③は404とは無関係だが同時に直した。** どちらも切り分けの過程で実物のHTMLを読んで見つかった実害のあるバグ（リンク切れ・本文へのコメント混入）で、同じ関数の中にある。

## 確認結果

- 修正後に本番の下書きを作り直し、**ユーザーがエディタで開けることを確認**（下書き `174599831`）
- 本文画像11点すべてが `figcaption` 付き figure で埋め込まれ、`failed_images` は空
- 変換のユニット確認: HTML コメントが出力されないこと、`Opportunity_(rover)` の URL が最後まで href に入ること、figure に `figcaption` が付くことを確認
- 切り分けに使ったテスト下書き10件と、開けなかった旧下書き2件はユーザーが削除済み

## 今後の課題

- **note の非公開 API を使う実装は、ローカル検証だけを「確認結果」にしない。** 今回のように、変換したHTMLが note の内部形式として妥当かは、実際に下書きを作ってエディタで開くまで分からない。w002 spec のフロー16 に「下書きを開いて表示を確認する」ところまで含めるか検討する
- 画像のキャプションを `figcaption` に入れる方式に変えれば、本文の段落として置いている現在のクレジット表記を figure に内包できる（表示の見え方が変わるため要検討）
