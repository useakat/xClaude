## 背景・動機

チャンドラセカール記事（W002・モードC）の制作で、フロー16（note 下書き保存）に進もうとした時点で `output/index.md` が存在しなかった。

spec を調べたところ、**`output/index.md` を作る工程がどこにも定義されていなかった**。spec が言及しているのは次の4箇所だけで、いずれも「すでに存在している前提」で書かれている。

| 箇所 | 記述 |
|---|---|
| ファイル構成の定義 | 置き場所の指定 |
| 参考情報の書式（2段階運用） | 公開版はマーカーを外し「文献の概要」にする |
| フロー10-4 | 「変更内容を output/index.md にも反映する」 |
| フロー11 | 「修正内容は output/index.md にも反映する」 |
| フロー16 | `output/index.md` を note に送る |

原因は、**spec がモードB（X長文の深掘り）を基準に書かれていた**ことにある。モードB では `output/index.md`（X長文本文）が入力として最初から存在するため、生成工程が要らない。モードA・モードC では新規に作る必要があるが、その手順が抜け落ちていた。

あわせて、フロー15 以降（ネタ更新・note 下書き・Drive アップロード・完了メール）が毎回ユーザー確認を挟む運用になっており、確定物を送出するだけの工程で対話が発生していた。よーんから「15以降は確認なしに実行してよい」「完了メールは無許可で送ってよい」との指示があったため、spec に明文化した。

## 実施内容

- **フロー15.5「公開版 `output/index.md` の生成」を新設**。draft から公開版を作る6手順（画像配置・マーカー除去・参考情報の書き換え・画像埋め込み・キャプション・機械検証）を明記した。モードB は不要である旨も併記。
- **フロー10-4・フロー11 の記述を修正**。「output/index.md にも反映する」を「draft.md に対して行う（output/index.md はフロー15.5 で生成する）」に変更し、制作中に2つのファイルを並行維持しなくてよいことを明確にした。
- **フロー18 に「送信前の確認は不要」を追記**。
- **「その他」に、フロー15 以降は確認なしに続けて実行してよい旨を追記**。ただしエラーや `failed_images` が出た場合は止めて報告する条件を付けた。

### フロー15.5 に書いた内容

1. 画像を `output/images/` に登場順の連番付きファイル名で配置（長辺1600px程度に統一）
2. 本文の参照マーカー `[N]` をすべて削除
3. 参考情報の説明を「本文での参照内容」から「文献自体の概要」に書き換え
4. 各 H2 直後に `![alt](images/...)` を単独行で埋め込み（単独行でないと note 側で figure 化されない）
5. 画像直後の `> …` 行を figcaption にする。**CC BY-SA など帰属表示が必要な画像はここに必ずクレジットを書く**
6. マーカーの残存・画像とキャプションの数・参考情報の件数を python で機械チェック

## 確認結果

チャンドラセカール記事で、新設したフロー15.5 の手順どおりに `output/index.md` を生成し、フロー16 を実行した。

- 本文の残存マーカー: 0
- 画像埋め込み: 7枚（すべて単独行）
- キャプション: 7件（うちライセンス上必須のクレジット3件）
- 参考情報: 26件（すべて「文献の概要」に書き換え）
- note 下書き保存: `failed_images` 空・終了コード0

figcaption によるクレジット表記は、`scripts/send_note_draft.py` が画像直後の `> …` を figcaption に変換する既存仕様をそのまま使えることを確認した。

## 設計判断

**`output/index.md` の生成をフロー15.5（制作の終盤）に置いた理由。**

spec の元の記述（フロー10・11 で「output/index.md にも反映する」）に従うと、推敲のたびに draft と output の2ファイルを同期し続けることになる。今回の記事は推敲を3巡し、章ごとに数十回の修正を重ねたため、その方式では同期漏れが確実に起きる。本文が確定してから一度だけ生成するほうが安全で、実作業もそうなっていた。

## 今後の課題

- モードA でも同じ手順が必要になるが、今回検証できたのはモードC のみ。
- 本文が spec の上限10,000字を超えた場合（今回12,316字）の扱いが spec に定義されていない。超過を許容するのか、必ず圧縮するのかを決める余地がある。
