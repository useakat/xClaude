## 背景・動機

同日の [note 本文画像アップロードを API 仕様変更に追従](./20260812_note_body_image_upload_api_fix/) で挙げた「今後の課題」2点をそのまま実装した。どちらも、その障害対応の最中に実際に踏んだ問題である。

**① 再実行のたびに下書きが増える。** `send_note_draft.py` は常に新規下書きを作る仕様だった。今回、本文画像11点が失敗したあとスクリプトを直して再実行したところ、画像なしの下書き（`174469281`）と完成版の下書き（`174474109`）が note 上に2つ並んだ。どちらが最新なのかはタイトルからは分からず、消し忘れれば誤って古い方を公開しかねない。

**② 画像が欠けたまま次工程へ進めてしまう。** 失敗時は終了コード 2 が返るものの、標準出力の JSON に `failed_images` が並ぶだけで、フローを止める仕立てにはなっていなかった。今回は目視で気づけたが、11点すべてが落ちるような派手な失敗ではなく1〜2点だけ落ちた場合、そのまま Drive アップロードと完了メールまで進んでしまう。**画像が1点でも欠けた下書きは未完成**であり、ここは自動で止まるべき箇所だった。

## 実施内容

### `--note-id`（既存下書きの上書き更新）

```bash
python3 scripts/send_note_draft.py "<タイトル>" \
  --base-dir "$ART/output" --eyecatch "images/thumbnail.png" \
  --note-id 174474109 < "$ART/output/index.md"
```

- 指定時は新規作成 API（`POST /api/v1/text_notes`）を呼ばず、渡された ID に対して `draft_save` とアイキャッチ設定だけを行う
- 戻り値に `"mode": "create" | "update"` を追加。どちらの経路で動いたかがログに残る

### 画像失敗時の停止

- 終了コード 2 に加え、標準エラーへ次を出力する

  ```
  ERROR: 画像 N 点のアップロードに失敗しました。この下書きは未完成です。
  原因を直したうえで、同じ下書きに --note-id <id> を付けて再実行してください
  （新しい下書きを作らないため）。
  ```

- w002 spec フロー16 に停止条件を明記
  - **`failed_images` が空でなければフロー17以降へ進まない**
  - 再実行は必ず `--note-id` を付ける
  - `--no-images` フォールバックは「まず原因特定を試み、どうしても通らない場合のみ」に格下げ（今回のように原因を特定できるケースで、安易に画像11点の手貼り運用へ戻らないため）。今回の仕様変更の実例も注記した

## 変更ファイル

| ファイル | 変更内容 |
|---|---|
| `scripts/send_note_draft.py` | `create_draft()` に `note_id` 引数を追加し、指定時は新規作成をスキップ。戻り値に `mode` を追加。CLI に `--note-id` を追加。画像失敗時に stderr へ再実行手順を出力 |
| `projects/w002/spec.md` | フロー16 に「`failed_images` が空でなければ次工程へ進まない」「再実行は `--note-id`」を追記。`--no-images` を最終手段に格下げし、2026-08-12 の仕様変更を実例として注記 |

## 設計判断

**新規作成をやめるのではなく、`--note-id` を任意の引数にした。** 記事1本につき下書き1本を作るのが通常の使い方で、そこは引数なしのままにしたい。ID を渡したときだけ上書きに切り替わる形にすれば、通常フローの手数は増えない。

**「失敗したら自動で `--no-images` にフォールバック」はしなかった。** 画像なしで保存が通ってしまうと、成功したように見えて実際は手作業が11回発生する。今回の障害も、原因を特定すれば2行の修正で直った。止めて原因を見に行かせる方が、結果的に早い。

**停止条件はスクリプトと spec の両方に書いた。** スクリプトの終了コードだけでは、対話的に実行しているときに読み飛ばされる。spec 側に「進まない」と書くことで、フローを回す側の判断としても固定した。

## 確認結果

- **`--note-id` の更新動作**: 実記事の下書き `174474109` に対して実行 → `mode: "update"`・同じ note_id・本文画像11点の再アップロード成功。新しい下書きは作られないことを確認
- **失敗時の停止**: 存在しない画像を含む本文で実行 → 上記の ERROR メッセージが stderr に出力され、終了コード 2 で終了することを確認
- 失敗パスの検証には、削除予定だった空の下書き `174469281` を `--note-id` で指定して使った（検証のために新しい下書きを増やさないため）。この下書きはテスト本文が入った状態で note 上に残っているため、削除が必要
