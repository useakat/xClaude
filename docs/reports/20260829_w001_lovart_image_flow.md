## 背景・動機

W001 spec のフロー10 は「`thumbnail/` の `nanobanana-prompt.md` に沿って添付画像を用意する。画像生成自体は外部（nano banana）で行い」という記述のままだった。しかし直近の実運用（8/12 オポチュニティ販促）は既に lovart を使っており、`lovart-prompt.md` と生成物 `lovart/*.png` が残っている。W002 は 8/9、W003 は 8/15 に lovart へ移行済みで、**W001 の spec だけが実態から取り残されていた**。

ハッブル投稿の制作でこの乖離に気づいた（当初 spec 通り nano banana 用のプロンプトを作り、外部生成を依頼しようとしていた）。lovart は `/lovart` スキルで直接呼べるため、外部依頼は不要だった。

あわせて、この制作で2つの落とし穴に実際にはまったため、対策を spec に残す。

## 実施内容

### 1. フロー10 を lovart に書き換え

`design-brief.md` → `lovart-prompt.md` の順で作り、`/lovart` スキルで生成して `output/thumbnail.png`（16:9）に保存する流れに変更した。認証は `~/.bashrc` の `LOVART_ACCESS_KEY` / `LOVART_SECRET_KEY` にあり、Bash から使うときは `source ~/.bashrc` が要る点も明記（Bash ツールにはプロファイルが引き継がれず、最初の呼び出しが認証エラーになった）。

### 2. 年代考証の注意を追加

ハッブルの参照画像として最初に取得したのは ESA/Hubble の `heic0908c`（地球上空の全景）で、構図は理想的だった。しかしこれは **2009年 SM4 の撮影**で、写っている太陽電池パネルは 2002年 SM3B で交換された第3世代の濃紺のもの。本編が扱う 1990〜1993年は**金色〜琥珀色の初代パネル**であり、そのまま参照させると機体の姿が史実とずれる。

この期間の実写を探したが、当時ハッブルを撮れたのはシャトルの至近距離からだけで、「宇宙空間に単独で浮かぶ全景」という構図は原理的に存在しない（遠景写真は離脱時に撮られ、SM3B 以降に集中する）。**時代の正確さと理想の構図は実写では両立しない**と判明した。

解決策として、1990年の実写2枚を「パネルの色・形状の正解」、2009年の実写を「構図と本体形状の参照」と**役割を分けて複数枚を渡す**方式を採り、両立させた。

### 3. 生成のコツを追加

修正指示を重ねるたびに別の箇所が崩れる現象が起きた（扉が1枚→2枚→パネルが片側に寄る）。**参照画像を毎回添付していたにもかかわらず**発生したため、原因は「フォローアップ指示では lovart が自分の前回出力を編集し、指示箇所以外が自分の出力に引きずられる」ことと判断した。

要件を全部盛り込んだプロンプトで**新規スレッドから一発生成**に切り替えたところ、一度で全条件を満たす結果が得られた。この知見を spec に残した。

## 設計判断

**参照画像の役割分担を prompt に明記させた理由。** 複数の参照画像を単に添付すると、生成モデルはどれを何の手本にすべきか判断できず、年代の違うパネルを混ぜてしまう。「添付1はパネルの色の正解／添付3は構図の手本、パネルは真似しない」と役割を書き分けることで、初めて意図通りに分離できた。

**修正を重ねない方針にした理由。** 3回の修正で3回とも別の箇所が壊れた。編集の反復はコスト（クレジット）もかかるうえ収束しない。要件が固まっているなら一発生成のほうが速く確実。

## 確認結果

- ハッブル投稿で実際に適用し、1990年当時の金色パネル・16:9・機体全景＋地球・文字なしをすべて満たす画像を生成できた
- 参照画像の出典・用途・除外理由を `thumbnail/reference/SOURCES.md` に記録し、Drive にもアップロード済み
- 生成過程で lovart のクレジットが枯渇する事象があり、無制限モードでもエージェントの推論分にクレジットが要ることを確認した（メッセージ: `Unlimited covers generation models only — the agent that runs your request still needs a credit balance`）

## 今後の課題

- W002・W003 の spec にも同じ年代考証の注意が要るか未確認。題材が実在の機体・人物である以上、同じ落とし穴はありうる
- `design-brief.md` の「星のハローを控えめに」という指定は、3回試して安定して再現できなかった。生成モデルが「星＝シャープな点」という強い事前分布を持つためと思われる。実現困難な指定は brief に書かない、という判断基準はまだ言語化していない
