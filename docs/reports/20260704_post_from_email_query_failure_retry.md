## 背景・動機

X長文投稿の cron（17:00）が、INBOX に投稿対象メール（`【X長文】…`・15:06 着信）があったにもかかわらず「投稿対象メールなし」で終了し、取りこぼした。

調査の結果、件名は cron の検索クエリ（`subject:【X長文】 in:inbox -label:投稿済み`）に**正しくマッチ**しており（手動確認で1件ヒット）、着信も 17:00 より前だった。原因は **17:00 実行時に gws の Gmail クエリが空を返した（一時的失敗、所要7秒＝通常2〜3秒より長い）**こと。

`post_from_email.sh` は、gws クエリが空/失敗しても JSON パースで `threads` が取れず、「正常に0件」と同じ扱いで**無言スキップ（exit 20）**していた。「本当に0件」と「クエリ失敗」を区別できず、失敗時のリトライも通知も無かった。

## 実施内容

STEP 1（未処理スレッド取得）を次のように堅牢化：

- gws の応答を **「正常0件」「API エラー応答（`error` キー）」「JSON なし/不正」** に分類する python 判定に変更（rc=0/3/2）。
- 失敗（rc≠0）は **最大3回・5秒間隔でリトライ**。
- 3回とも失敗したら **`RESULT="failed"`（＝exit 1）で中断**し、`⚠ Gmail クエリが3回とも失敗…中断（要確認・投稿は行わない）` をログに明示。
- 応答先頭の非JSON行（`Using keyring backend: keyring` 等）は `find('{')` で読み飛ばして除去。

## 変更ファイル

| ファイル | 変更内容 |
|---|---|
| `scripts/post_from_email.sh` | STEP 1 のクエリ処理を、失敗/0件を区別しリトライ・中断する方式に置換 |

## 設計判断

- **失敗時は exit 1（20 ではない）**：ラッパー（`run_xlong_post.sh` 等）の z01 短文フォールバックは `rc=20`（対象なし）でのみ発火する。クエリ失敗でむやみに代替投稿しないよう、失敗は 1、対象なしは 20 と明確に分けた。
- **リトライ方式**：一時的な gws の遅延/認証ゆらぎを吸収するため 3 回リトライ。それでも失敗ならログに明示して中断（無言スキップを廃止）。「リトライ or 通知」の要件のうちリトライ＋明示ログで対応。
- keyring 情報行の混入にも耐えるよう JSON 先頭を検出してからパースする。

## 確認結果

- `bash -n scripts/post_from_email.sh` 構文 OK。
- 判定ロジック単体テスト（すべて期待どおり）:
  - 正常・1件（keyring 行付き）→ rc=0・最古1件を採用
  - 正常・0件 → rc=0・THREAD_ID 空（対象なし）
  - API エラー応答 → rc=3（失敗→リトライ）
  - 空文字 / 非JSON → rc=2（失敗→リトライ）

## 今後の課題

- 「エラー通知」（Gmail/LINE 等への失敗アラート）は未実装（今回はリトライ＋ログ明示で対応）。無人 cron の失敗を能動的に知りたい場合は、3回失敗時に `check_auth` 系の通知に相乗りする案を検討。
- 今回取りこぼしたメール自体は INBOX に残存（次回 cron で拾える）。
