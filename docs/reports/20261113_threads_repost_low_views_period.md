## 背景・動機

Threads投稿一覧（スプレッドシート `1_0317hOqbgGfcSZQ9D9-JlwgqvKxzQuRaw08U-5nw0c`）を 5 月以降で週ごとに集計すると、**2026-07-24 〜 09-23 の約 2 か月間、本体投稿 98 本がすべて 2 桁〜100 views 台**（週中央値 9〜28、100 views 超は 0 本）に抑えられていた。9/24 から中央値 約 1,000 に戻っており、内容ではなく配信側の要因で届いていなかったと判断できる。

この期間の 98 本は内容に関係なく読まれていないため、**同じ内容を古い順に 1 日 1 本ずつ再投稿**して本来の反応を取り直すことにした。よーんの決定（11/11）：

- 毎日 18:00 に【threads投稿】の Gmail 下書きを 1 本作る（既存のメール→Threads 投稿パイプラインに乗せる）。よーんが下書きを確認・必要なら修正して自分宛に送信し、cron が投稿する
- 元投稿に付いていた続きのセルフリプ（25 本）は付ける。ただし **URL を含むセルフリプは除外**
- 本文は原文のまま。時期依存の語（「今日」「速報」など）はよーんが下書きで直す
- 画像は下書き作成時点のシートの最新 CDN URL を使う（毎朝 05:00 の `fetch_threads_posts.py` が更新する署名付き URL、約 4 日で失効）

## 実施内容

- `scripts/make_threads_repost_draft.py` を新設（`make_threads_draft.py` の `build_body` / `cell` / `create_gmail_draft.sh` 呼び出しを import して流用）
  - **キュー** `logs/threads_repost_queue.csv`（git 管理。列：順番, 元投稿URL, 元投稿日時, 種類, 画像, 元views, 下書き作成日, 再投稿URL）。`--init` で 7/24〜9/23 の本体投稿（親投稿URL 空）98 本を古い順に書く。既存ファイルがあれば上書きしない
  - **通常実行**：`下書き作成日` が空の先頭 1 行の下書きを作り、今日の日付を書く。`--redo N` は順番 N を作り直す（画像 URL 失効時の手当て）。`--dry-run` は件名・本文の表示のみ
  - **下書きの中身**：先頭に `[メモ]`（順番 n/98、元 URL、元投稿日時、元 views、時期依存語の列挙、カルーセルなら「1 枚目のみ」の注記、続きリプの件数と除外数）→ `[投稿文]` 原文 → `[画像URL]` シートの現在の F 列 → `[リプ]` 続きセルフリプ（親投稿URL をたどって時系列に集め、`http` を含むものを除き、複数なら `=====` 行で連結して `post_threads.py` の返信チェーン分割に乗せる）→ `[リプ画像URL]`。`[XURL]` は付けない。件名は `【threads投稿】` ＋本文冒頭 20 字（既存の Gmail 検索条件に合う）
  - **再投稿URL の自動突合**：下書き作成の前に、キュー開始日以降の本体投稿のうち本文先頭 60 字が一致するものを `再投稿URL` に書く。元 views と再投稿 views を後から比べるため
- `scripts/run_threads_repost_draft.sh` を新設（flock・`logs/threads_repost_draft.log`・非 0 終了時に `send_gmail.sh` で「【threads再投稿】下書き作成失敗」を通知）
- `scripts/run_threads_post.sh` のヘッダに 09:00 cron を記載（実体は無改修）
- VPS crontab（git 管理外）に 2 行追加
  - `0 18 * * * run_threads_repost_draft.sh` — 下書き作成
  - `0 9 * * * run_threads_post.sh` — **投稿の専用枠**。従来【threads投稿】メールは X 投稿 cron（06/12/17/20）で「X に投稿が無かったときだけ」拾われるフォールバックだったため、X 投稿が続くとメールが残り続ける。朝 9 時に必ず拾う枠を足した（20:00 のフォールバックで先に拾われても、受信箱の最古から処理するので順番は崩れない）
- 既存は無改修：`post_threads.py`、`post_threads_from_email.sh`、`record_output.py`、`fetch_threads_posts.py`

## 設計判断

- **既存パイプラインに乗せる**：再投稿を直接 API で行う案もあったが、よーんが本文を確認・修正できる工程を挟むため Gmail 下書き経由にした。投稿側（`post_threads_from_email.sh`）は無改修で済む
- **順番は受信箱の最古から**：下書きを削除すればスキップ、送信すれば翌朝投稿。キューには `下書き作成日` だけ残り `再投稿URL` が空＝スキップと分かる
- **メモ内にタグ文字列を書かない**：当初メモに「`[リプ]` に連結」と書いたところ、`extract_tag.py リプ` がメモ内の `[リプ]` から本物の `[/リプ]` までを本文として拾う不具合が出た。メモの文言を「続きリプ n 件をセルフリプとして連結」に変えて解消。今後も `[メモ]` 内に `[投稿文]` 等のタグ名を書かない
- **リンク入りセルフリプの除外**：note 導線などのリンクは当時の文脈に依存するため外し、必要ならよーんが下書きで足す

## 確認結果

- `--init --dry-run`：98 件、7/24 18:53（木星の大赤斑）→ 9/23 20:00 の順で生成
- `--dry-run` 個別確認：順番 4（カッシーニ）は続きリプ 1 件が `[リプ]` に入る／順番 35 はリンク入りリプのみで `[リプ]` 無し＋メモに注記／順番 8（カルーセル）は 1 枚投稿の注記
- 生成本文を `extract_tag.py` に通し、投稿文・画像URL・リプが正しく取れ、リプ画像URL・XURL は無し（rc=1）になることを確認。メモ内タグ文字列の不具合はこの確認で検出・修正
- ラッパー経由の実行で Gmail 下書き「【threads投稿】実は、木星の大赤斑はだんだん小さくなって」が作成され（`gws gmail users drafts get` で確認）、キューの順番 1 に `下書き作成日=2026-11-12` が書かれた
- 実装コミット `e0f04d9`（対象 4 ファイルのみ。11/8 の autostash 混入は再発せず、commit 前に `git diff --cached` が空であることを確認）

## 今後の課題

- 翌日 18:00 の実行で `再投稿URL` が自動で埋まることを確認する（まだ 1 本目が投稿されていない）
- 98 本が終わる約 3 か月後に、元 views と再投稿 views を並べて集計する（週次振り返りに載せるかは別途）
- 画像 URL が 4 日超で失効して投稿に失敗したときは `--redo N` で作り直す運用。下書きを 4 日以上放置しないこと
