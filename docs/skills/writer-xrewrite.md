## スキル説明

過去の伸びた X 投稿（半年以上前・未リライト・グレード S/A 優先、無ければ IMP 1 万以上の上位 20）を 1 本選び、4 要素に分解して「伸びた理由」を特定したうえで、回数で決まる方式（①冒頭を変える→④驚きの軸を変える→②結末先行→③主人公・視点を変える）でリライトし、z01 と同じチェック（reader/fact/critic/brand/yohn）を通して件名【リライト】の Gmail 下書きを 1 本作る。what_id は元の what_id に r を付ける（W001r/W003r/z01r）。ユーザー確認なし全自動。投稿は行わない。

## 詳細内容

過去の伸びた投稿を**別の切り口で読者に届け直す**。単なる言い換えではなく、元投稿の「伸びた理由」を残したまま、他の要素を動かす。**投稿は一切行わず、Gmail 下書きを 1 本作るだけ。全 STEP を自動で実行する。ユーザーの確認・承認は不要。**

> 設計の出典：2026-11-14 の計画（半年以上前・S/A 優先・回数で方式固定・4 要素分解・避けたいこと 5 項目）。フック型の実測データは `outputs/reports/20261113_x_top100_hook_list.md`（自アカウント）と `outputs/reports/20261113_x_others_top100_hook_types.md`（競合 3 アカウント）。

# STEP 1: 元投稿の選択（`scripts/rewrite_pool.py`）

```bash
python3 scripts/rewrite_pool.py pick
```

- JSON が返る。主なキー：`tweet_id` `url` `date` `text`（元本文全文）`chars` `imp` `grade` `what_id` `what_id_source`（`outputs`＝記録あり／`length`＝字数で推定）`new_what_id`（元 what_id＋r）`rewrite_count`（過去のリライト回数）`prev_methods` `prev_elements` `method_candidates`（この回で使える方式。順番どおり・未使用のみ）`pool`（`SA`＝S/A プール／`TOP20`＝IMP 1 万以上上位 20）
- `{"error": "候補なし"}`（exit 3）なら STEP 8 の枯渇報告を出して終了する。下書きは作らない
- 候補の条件（スクリプト側で判定）：本体投稿・投稿日が 180 日より前・W006/W004/W007 と質問回答と URL 紹介を除外・リライト済みは最後のリライトから 180 日未満なら除外（1 本あたり年 2 回まで）
- **STEP 2 の分解で「リライトに向かない」と判断した場合**（時事・サイト紹介・日常報告・引用前提で単体で読めない等）は、その tweet_id を `--exclude` に付けて再度 pick する（最大 3 回。`--exclude` はカンマ区切りで累積）：

```bash
python3 scripts/rewrite_pool.py pick --exclude {tweet_id1},{tweet_id2}
```

選んだら、`what_id` に応じて STEP 0-2 のプロジェクトファイルを Read する。

# STEP 2: 元投稿の分解（4 要素と伸びた理由）

元本文（`text`）を 4 要素に分けて、各 1〜2 行で書き出す。

| 要素 | 確認すること |
|---|---|
| フック | 最初の 1〜2 文。どの型か（台詞／○年前の今日／口火／実は・旧常識反転／問いかけ／発見共有／物語一文／場面描写／会話劇） |
| 驚き | 読者の常識を裏切る情報は何か。技術的／人間的（執念）／歴史的のどれか |
| 展開 | 何が起きたのか。構成の型（解説型／時系列物語型／結末先行型／会話劇型／台詞型／問いかけ型／旧常識反転型／場面描写型） |
| 余韻 | 読後に何を残すか。締めの一文 |

続けて次を 1 行ずつ決める：

- **伸びた理由（1 行）**：IMP・グレード・本文から、4 要素のどれがどう刺さったかを 1 文で言語化する
- **刺さった要素**：`フック` / `驚き` / `展開` / `余韻` のうち 1 つ。**この要素はリライトで触らない**（守る対象）
- **元投稿の事実リスト**：本文に出てくる数値・固有名詞・年月日・因果を箇条書きで抜き出す（STEP 5 の差分チェックと STEP 6 の fact 判定に使う）

# STEP 3: 方式の決定

`method_candidates` の先頭から順に見て、**刺さった要素を壊す方式を飛ばし**、最初に残った方式を採用する。

| 刺さった要素 | 飛ばす方式 | 理由 |
|---|---|---|
| フック | ①冒頭を変える | 刺さった 1 文目を捨てることになる |
| 驚き | ④驚きの軸を変える | 驚きそのものを取り替えてしまう |
| 展開 | ②結末先行 | 順序を崩すと展開の効果が消える |
| 余韻 | （なし） | どの方式でも締めは残せる |

方式の順番（`rewrite_pool.py` の `METHOD_ORDER` と同じ）：
- 通常：①冒頭を変える → ④驚きの軸を変える（技術→執念・歴史） → ②結末先行 → ③主人公・視点を変える
- 元が W001 系（すでに執念の物語）：①冒頭を変える → ②結末先行 → ③主人公・視点を変える → ④驚きの軸を変える

全部飛ばされた場合は、順番の最初の方式を使う。

## 各方式の内容

- **①冒頭を変える**：本文はほぼ維持し、最初の 1〜2 文だけを別のフック型に差し替える。差し替え先は元投稿で使っていない型から、実測中央値の高い順に選ぶ：台詞始まり（自アカウント中央値 15 万）／○年前の今日（11.5 万）／子どもの質問・会話劇（競合 1,499 万）／場面描写（競合 164 万）／問いかけ（競合 77.5 万）／発見共有（2.1 万）。**口火（「これ、ヤバすぎる話なんだけど聞いてくれ」系）は使い回しで IMP が下がっている実測があるので選ばない**
- **④驚きの軸を変える**：元が技術的な驚き（仕組み・数値）なら、人間の執念（なぜ諦めなかったか・誰の判断か）か歴史的な意味（この出来事が後に何を残したか）へ軸を移す。plan.md の「執念＝中身」に寄せる方向
- **②結末先行**：時系列（異常発生→対応→結果）を逆転し、驕くべき結果から入って「何が起きたのか」→「どう立ち向かったか」の順に書く
- **③主人公・視点を変える**：探査機側↔人間側（開発チーム・ある技術者の判断・地上管制室）で主人公を替える。「何が起きたか」から「誰がどう立ち向かったか」へ
- **全方式に共通して「短くする」を適用する**：説明を削る・専門用語を減らす・同じ意味の文を統合する・最も印象的な事実を残す。**元より長くしない**

## 字数の帯

- 元が 140 字以内（z01 系）：135〜140 字
- 元が 141〜300 字（W003 系）：元の 60〜100%
- 元が 300 字超（W001 系）：元の 60〜100%、かつ 700 字以内を目標（元が 700 字超なら短縮が必須）
- 字数は改行・空白を除いた本文のみで数える

# STEP 4: 3 案を書いて 1 案を選ぶ

採用した方式の中で、**具体化の違う 3 案**（A / B / C）を書く：

- ①冒頭：差し替え先のフック型を 3 種類
- ④驕きの軸：執念軸／歴史軸／人物（判断）軸
- ②結末先行：先頭に置く「結末」の切り出し方を 3 種類（数値／台詞／情景）
- ③視点：主人公候補 3 人（機体・チーム・個人、または地上管制室）

3 案それぞれに「伸びた理由を保てているか」を 1 行で自己判定し、**1 案を選んで理由を 1 行**書く。不採用 2 案は冒頭 2 文と選ばなかった理由だけを `[チェック証跡]` の下に `[不採用案]` として残す（よーんが下書きで差し替えられるように。タグ名は `[投稿文]` `[最終原稿]` と絶対に重ねない）。

事実は元投稿の範囲内で書く。④や③で元本文にない事実（別の人物の判断・後年の影響など）を足す場合は、足した事実を列挙しておく（STEP 6 の fact 判定に使う）。

# STEP 5: リライト差分チェック（避けたいこと 5 項目）

選んだ案を元本文と並べ、次を機械・目視で確認する。該当したら書き直してから STEP 6 へ進む。

1. **単語を入れ替えただけになっていない**：元本文と連続 20 字以上一致する箇所が、採用方式で動かさない部分（①の本文、②の中段など）以外に残っていないか
2. **文の順番を少し変えただけになっていない**：方式の狙い（新しい入口／逆転した順序／別の主人公／別の驚きの軸）が 1 行で言えるか
3. **元の具体的な数字・固有名詞を削っていない**：STEP 2 の事実リストの数値・固有名詞が本文に残っているか。意図的に落としたものは理由を書く（「短くする」で落とすのは説明文であって、刺さった数字ではない）
4. **感情表現が過剰になっていない**：「震える」「ヤバい」「泣ける」等の感嘆・煽りを元より増やしていない
5. **元より長くなっていない**：下の差分スクリプトの字数行で確認する（元より長ければ exit 1）

## 変更箇所の確定（`scripts/rewrite_diff.py`）

元本文を `/tmp/xrewrite_orig.txt`、案を `/tmp/xrewrite_new.txt` に Write してから実行する：

```bash
python3 scripts/rewrite_diff.py /tmp/xrewrite_orig.txt /tmp/xrewrite_new.txt
```

文単位で元と突き合わせ、**【チェック対象】**（新規／微修正／削除前後の文）と**【元から消えた文】**を出す。

- 【チェック対象】が STEP 6 でチェック指摘を反映してよい範囲。**元投稿は半年以上前に実際に伸びた文章なので、それ以外の文は「実績で合格済み」と扱い、今の基準で書き直さない**（試運転では方式①なのに元と同一の文が 36 文中 3 文しか残らなかった。その反省）
- 【元から消えた文】に STEP 2 の事実リストの数値・固有名詞が含まれていたら、上記 3 の確認に戻る
- 改稿のたびに再実行し、チェック対象を更新する

# STEP 6: 品質チェック（実起動・証跡を残す・変更箇所に絞る）

各 `/check-*` は Skill として**実起動**する。自己検品での代替は禁止。無人フローなので未収束でも止めず、結果を証跡と完了報告に残す。

## 6.0 全方式共通：変更箇所フィルタ

- 読者役・検品役には**全文**を渡す（接続の判定に全文が要る。変更箇所は教えない＝隔離を守る）
- 返ってきた指摘は writer 側で選別し、**STEP 5 の【チェック対象】の文に掛かるもの、または変更が原因で起きたもの（削った文の前後の詰まり・新しい冒頭と本文の接続）だけ反映する**
- それ以外は「元投稿由来・未反映」として `[チェック証跡]` に件数と要点を残す。元投稿の事実への疑義（数え方・帰属など）も同じ扱い
- check-yohn を起動するときは、プロンプトに「**元投稿の範囲外にある事実の加筆を求める指摘は出さない**（この原稿は過去投稿のリライトで、事実は元投稿の範囲内に限る）」を 1 行足す
- 改稿したら `rewrite_diff.py` を再実行し、チェック対象を更新し、元より長くなっていないことを確認する

## 6-A 方式①（冒頭を変える）：軽量チェック

本文は元投稿で実績済みなので、冒頭差し替えで壊れうる 3 点だけを見る。brand / yohn は**省略**し、証跡に「省略（方式①・本文は元投稿で実績済み）」と書く。

| 順 | チェック | 見るもの | 最大ループ |
|---|---|---|---|
| A-1 | `python3 scripts/x_fold_split.py /tmp/xrewrite_new.txt` | 切れ目が謎・宣言・数字の直後に来ているか（語の途中・説明の途中なら可視ブロック内の語順・字数で調整） | 機械 |
| A-2 | `/check-reader --fold plan.md {本文}` | 新しい冒頭で「さらに表示」を押すか | 2 |
| A-3 | `/check-reader plan.md {本文}` | 新しい冒頭が立てた謎・台詞が本文で回収・接続されているか（元で冒頭要素があった位置の文が書き換わっているはず）。6.0 のフィルタで変更箇所の指摘だけ反映 | 1（改稿 1 回まで） |
| A-4 | `/check-fact {本文}` | 冒頭に元本文にない台詞・年号・数値を持ち込んだ場合のみ | 3 |

## 6-B 方式②③④：全文チェック

文の大半が新しくなるので従来どおり全段を回す（6.0 のフィルタは適用する。元から残した文への指摘は未反映）。

| 順 | チェック | 条件 | 最大ループ |
|---|---|---|---|
| B-1 | `python3 scripts/x_fold_split.py` → `/check-reader --fold plan.md {本文}` | 常に | 2 |
| B-2 | `/check-reader plan.md {本文}` | 常に | 3（指摘に本文で答える形で改稿） |
| B-3 | `/check-fact {本文}` | 元本文にない数値・固有名詞・因果を足した場合のみ。足していなければ「元投稿の範囲内のため省略」 | 5 |
| B-4 | `/check-critic --field {分野} {本文}` | 方式が ④、または ③で主張の因果を組み替えた場合のみ | 3 |
| B-5 | `/check-brand {プロジェクトの brand.md} {本文}` | 常に。brand.md は STEP 0-2 で読んだプロジェクトのもの（W001r → `projects/w001/brand.md`、W003r → `projects/w003/brand.md`、z01r → `projects/z01/brand.md`） | 5 |
| B-6 | `/check-yohn {ペルソナ} {本文}` | 常に。ペルソナは `.claude/skills/check-yohn/persona-yohn_{w001|w003|z01}.md` を元 what_id で選ぶ。6.0 の加筆禁止文言を付ける | 3 |
| B-7 | `/check-reader plan.md {本文}` 最終 1 パス | B-3〜B-6 で本文の中身が変わった場合のみ。**改稿せず提示のみ**（完了報告に「最終 reader 指摘（未修正・要確認）」として列挙） | 1 |

**確定ゲート**（機械チェック）：
1. 字数が STEP 3 の帯の中にある
2. 本文に `[投稿文]` `[/投稿文]` `[最終原稿]` `[/最終原稿]` の文字列が含まれない
3. ハッシュタグ・URL・CTA を含まない

ここを通った本文が確定稿。**STEP 7 以降で本文を変更しない。**

# STEP 7: Gmail 下書き作成（1 回だけ・以後触らない）

**下書きは 1 回だけ作成し、作成後は一切触らない**（2 回目の作成・更新・削除は禁止。修正版はチャットで提示するだけ）。

## 7-1: 本文ファイル `/tmp/xrewrite_mail.txt` を Write

```
what_id: {new_what_id}

[メモ]
```

- 画像は付けない

## 7-2: 件名と日時

- トピック要約：確定稿の核心キーワードを名詞句で 10〜15 字以内
- 日時：`TZ=Asia/Tokyo date '+%Y%m%d %H:%M:%S'`

## 7-3: 下書き作成

```bash
bash scripts/create_gmail_draft.sh \
  --to useakat@gmail.com \
  --subject "【リライト】{トピック要約} {YYYYMMDD HH:MM:SS}" \

```

成功判定は `✓ 下書き作成完了` の出力。クラウド環境では Gmail コネクタの `create_draft` を使う。

# STEP 8: 記録と commit

1. リライト記録を追記する：

```bash
python3 scripts/rewrite_pool.py record \
  --tweet-id {tweet_id} --method "{方式}" --element {刺さった要素} \
  --new-what-id {new_what_id} --subject "{件名}"
```

2. フック型を `logs/hook_records.csv` に 1 行追記する（プロジェクト列は `{new_what_id}`。フック型は確定稿の冒頭の型、冒頭 15 字は確定稿の先頭 15 文字そのまま。半角カンマは含めない）：

```bash
REPO=$(git rev-parse --show-toplevel)
echo "$(TZ=Asia/Tokyo date +%F),{new_what_id},{フック型},{冒頭15字},rewrite[{tweet_id}],{方式},{謎},{自分事}" >> "$REPO/logs/hook_records.csv"
```

3. **この 2 ファイルだけ** commit & push する（無人フローなので push しないと記録が消える）：

```bash
bash "$REPO/scripts/commit_and_sync.sh" "record(rewrite): {new_what_id} リライト記録を追加" logs/rewrite_records.csv logs/hook_records.csv
```

リモート環境で push が認証エラーなら GitHub MCP で master へ push する。

# その他

- **投稿は一切行わない。** X 投稿は cron 定時実行のみ
- **下書きは 1 投稿につき 1 回だけ作成し、作成後は一切触らない**
- 事実は元投稿の範囲内が原則。足した事実は必ず `/check-fact` を通す（STEP 6.2）
- 時事ネタとの絡めは本スキルの対象外（時事ネタ起点の投稿は別フロー）
- 同じ元投稿のリライトは 180 日間隔・年 2 回まで（`rewrite_pool.py` が判定）
- 日報・週報の what_id 名称表に `W001r` `W003r` `z01r` を足す作業は、初回投稿後に別途行う
