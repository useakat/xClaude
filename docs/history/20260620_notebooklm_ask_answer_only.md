## 原因：フォークした subagent の「ストリーム idle タイムアウト」

エラー文 `Stream idle timeout - partial response received` は、**NotebookLM や Python のタイムアウトではなく、フォークされた subagent と LLM API の間のストリームが「無音」になって切れた**ことを示しています。仕組みはこうです。

1. `/check-fact-lim` は **forked subagent** として動く。
2. その subagent が `notebooklm_manager.py ask` を **1回の Bash 呼び出しでブロッキング実行**する（`cmd_ask`：`result = await client.chat.ask(...)` → `print(result)`、`scripts/notebooklm_manager.py:62-65`）。
3. NotebookLM の回答生成は、長い質問だと **60〜180秒以上**かかる。その間、subagent は**トークンを1つも出力しない**＝ストリームが idle。
4. LLM API 側の idle 上限が、NotebookLM の応答待ち時間より短い → **待っている最中に接続が切られる**。

これを**悪化させている2要素**：

- **質問が長く、生成が長い**：ファクトチェックは16項目＋本文全体を一度に投げるため、NotebookLM の生成が長時間化 → idle 時間が伸びる。
- **出力が巨大**：`cmd_ask` は `print(result)` で **AskResult を丸ごと**出力する。`answer` だけでなく全 `ChatReference` の `cited_text`・ソース抜粋まで含むため、**1回で 665KB〜2.3MB**（実測）。仮に返ってきても、subagent がこの巨大出力を読み込むのが重く、別の限界にも触れやすい。
- 補足：`cmd_ask` のクライアントには `timeout=` が無い（`deep_research` は `timeout=120` 指定済み）。Python 側で打ち切られず、idle が最大化する。

**なぜ私の直接実行は成功したか**：私はメインループで Bash を `timeout=280000ms` の前景実行で同期待ちし、さらに出力を `python3 -c` で `answer=` だけ抽出するフィルタに通している。巨大出力もコンテキストに入らず、ストリーム idle 制約も受けない。フォークした subagent はこの2つの保護がないため idle で落ちる。

## 対策（効果順）

1. **出力を `answer` だけに絞る**：`cmd_ask` に `--answer-only` を追加（または skill 側でフィルタ経由）。MB→KB に縮小。**1行修正で最も効く。**
2. **質問を分割**：16項目を4〜5項目ずつの短い ask に割る。生成が速くなり idle 窓に収まる。
3. **背景実行＋ポーリング**：ask をバックグラウンドに投げ、定期ポーリングでストリームを生かす。
4. `cmd_ask` に `timeout=` を追加（防御的に早期失敗）。
5. 長い照合は**メインループでインライン実行**する（今回私がやった方法）。

`notebooklm_manager.py` または `check-fact-lim/SKILL.md` の修正が必要です（スクリプト/スキル編集のため、適用前に確認します）。**対策1＋2**（出力削減＋質問分割）を入れるのが費用対効果が高いと考えますが、どこまで直しますか。

## 呼び出し回数
- **STEP1 完全性チェック：1回**
- **STEP2 ファクトチェック：最大5回ループ**（スコア95未満なら修正文案を入力に再送）
- → 最大 **6回**の ask。

## 各 ask の中身
1. **質問文を組み立てて一時ファイルに保存**：固定の指示文（レビュー観点＋出力フォーマット指定）の末尾に、`【チェック対象の文章】` として **本文テキストを丸ごと埋め込む**。それを `/tmp/check_fact_lim_prompt.txt` に書き出す。
2. **前景ブロッキングで1回呼ぶ**：
   ```bash
   python3 $(git rev-parse --show-toplevel)/scripts/notebooklm_manager.py ask <notebook_id> "$(cat /tmp/check_fact_lim_prompt.txt)"
   ```
3. **出力をそのまま表示する**（SKILL に明記）。＝ `cmd_ask` の `print(result)` が返す **AskResult 丸ごと**（answer＋全 `ChatReference` の `cited_text`・ソース抜粋、数百KB〜MB）を、フィルタせず subagent のコンテキストに取り込む。
4. STEP2 では毎サイクル、**また本文全体を埋め込んで投げ直す**（上書き再送）。

## つまり、タイムアウトに直結する3点
- **毎回ブロッキングで長時間待つ**（背景実行・ポーリングなし）→ ストリーム idle。
- **毎回 本文全体を送る**（質問が長い→生成が長い）→ 待ち時間が伸びる。最大6回。
- **出力を絞らない**（answer だけ抜く処理がない）→ MB級の結果を最大6回読み込む。

要するに「本文全部を入れた長い質問を、前景で待ちながら、結果を丸ごと受け取る」を最大6回やる作りで、フォーク実行のストリーム idle 上限を超えやすい、というのが現状です。

修正方針（出力を answer だけに絞る／質問分割／背景＋ポーリング）の中で、どれを入れるか決めれば計画に落とします。

## 方法A：セクション分割（いまの方式に最小変更）
STEP2 のループの中で、本文を **H2 セクション単位**に割って、セクションごとに ask する。

- 本文を `導入 / H2-1 / … / H2-5` に分解（`## ` で split）。
- 各セクションだけを `【チェック対象の文章】` に入れて ask → セクション別に `## スコア` と `## 修正文案` を得る。
- 集約：全セクション ≥95 なら合格。各セクションの指摘を結合してサマリーにする。
- 次ラウンドは **95未満のセクションだけ**を再 ask（全文を投げ直さない）。

特徴：1回の ask が 1/6 サイズ → 生成が速く・出力も小さく idle に収まる。SKILL の「prose を採点して修正文案を返す」契約をそのまま保てる。欠点は呼び出し回数が増えること（セクション数ぶん）と、セクション跨ぎの整合（呼称・前方参照）は見えにくくなること。

## 方法B：主張抽出して分割（方式そのものを変える）
いまの SKILL は「散文を渡して誤りを探させる」ので、**分割すべき"項目リスト"がそもそも無い**。そこで ask の前に一段はさむ。

- そのリストを（必要なら5項目ずつ batch で）ask → NotebookLM は各項目を **OK / NG / 不明＋該当ソース**で返す。
- NG/不明 を本文の該当箇所に対応づけて、修正文案は Claude 側で作る（or 小さな追い ask）。

特徴：質問も回答も最小（散文ではなく短いリスト）。今回1回で通った実績の形。欠点は SKILL のフロー改修が大きい（抽出ステップ追加、修正文案の生成箇所が notebook→Claude に移る）。
