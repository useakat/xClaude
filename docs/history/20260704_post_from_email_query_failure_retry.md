## 結論：件名は問題なし。原因は別

1. **件名はちゃんとマッチします** — cron と同一クエリ（`subject:【X長文】 in:inbox -label:投稿済み`）で**今このメールが1件ヒット**します。`【X長文】20260704...` の形式は引っかかります。
2. **メールは 15:06 に INBOX 着信**（ラベル: IMPORTANT / SENT / INBOX）。17:00 より前から inbox にあったので**着信タイミングの問題でもない**。
3. それなのに 17:00 の cron は「投稿対象メールなし」。しかも**所要 7 秒**（普段は2〜3秒）。→ **17:00 実行時に Gmail クエリが空を返した（一時的な失敗）**可能性が高いです。

`post_from_email.sh` は、gws クエリが空/失敗しても「対象メールなし」と同じ扱いで**無言でスキップ**します（成功時も失敗時も見分けがつかない）。過去には cron 実行でも投稿成功例があり（2026-05-15 17:00:05）、恒久故障ではなく**一時的な取りこぼし**とみられます。

## つまり
- 件名の直しは不要。
- 今日の未投稿は「17:00 時点で Gmail クエリが空を返した」ため。メール自体は今も inbox にあり、次回 cron（明日17:00）で拾えるはずですが、**今日分としては取りこぼし**です。

## 変更内容（`scripts/post_from_email.sh` の STEP 1）
- gws クエリの結果を **「正常0件」「API エラー応答」「JSON なし/不正」** に分類。
- 失敗（rc≠0）は **最大3回・5秒間隔でリトライ**。
- 3回とも失敗したら **`RESULT=failed`（exit 1）で中断**し、ログに `⚠ Gmail クエリが3回とも失敗…中断` を明記。→ 従来の「無言で対象なし扱い（exit 20）」を解消。
- 失敗時は exit 1 なので、**ラッパーの z01 フォールバック（rc=20 のみ発火）も暴発しません**（クエリ失敗でむやみに代替投稿しない）。
- keyring 情報行など先頭の非JSON行も除去して堅牢化。

これで今日のような「メールはあるのにクエリが空を返して無言スキップ」は、リトライ＋失敗を明示する形になりました。
