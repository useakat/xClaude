*[ツール: `Bash`, `Bash`, `Read`, `Bash`]*

原因は、予約ファイルの取り込み処理（`scripts/postcal_import.py`）です。画面で削除しても、10 分ごとの取り込みが同じ予約ファイルを新しい下書きとして登録し直しています。

## 仕組み
- スキルが作った投稿は `outputs/scheduled-posts/` の予約ファイルが元で、取り込み処理が 10 分ごとにそれを postcal に登録します。
- 画面の「削除」は postcal の DB から消すだけで、予約ファイルは残ります。
- 取り込み処理は「DB から消えている → 新規として作り直す」という作りになっています（`scripts/postcal_import.py:290`）。

## 実際に起きていたこと
取り込みログと DB を照合すると、次の 4 件が削除後に登録し直されて、いま下書きとして残っています。

| 予約ファイル | 経過 | 現在 |
|---|---|---|
| アポロ12号 落雷と管制官 | #18・#22・#29 を削除（3 回復活） | #32 下書き（11/28 6時） |
| クラゲ銀河 尾で生まれる星 | #24 を削除 | #30 下書き（11/29 6時） |
| 系外銀河 塵の奥のベンゼン | #25 を削除 | #31 下書き（11/30 6時） |
| 神舟5号 ポゴ振動 | #26 を削除 | #27 下書き（12/1 6時） |

復活するのは下書きとしてなので、「投稿予約」を押さない限り投稿はされません。

## 修正案
`scripts/postcal_import.py` を次のように変えます。

- 一度登録した予約が DB から消えていたら「画面で削除済み」と記録し、以後は登録し直さない。
- 例外として、削除後に予約ファイルの本文が書き換えられた場合（改稿版の push）だけは、新しい下書きとして登録する。

修正後に上の 4 件を画面でもう一度削除すれば、今度は戻ってきません。

この内容で `scripts/postcal_import.py` を修正してよいですか？ 本文が書き換えられても復活させない形がよければ、そのようにします。

## よーん *(22:19 JST)*

画面の削除を押したら、予約ファイルも削除するようにできない？

### Claude *(22:19 JST)*

*[ツール: `Bash`]*

できます。ただし、画面の「削除」でファイルを直接消す形はおすすめしません。次の 2 段階にするのがよいと考えます。

## おすすめの形
1. **画面で「削除」を押した時点**で、postcal がその予約を「削除済み」と記録します。この時点で、取り込みによる復活は止まります。
2. **10 分ごとの取り込み処理**が、削除済みの予約ファイルを消して master に commit・push します。

## 直接消さない理由
- **VPS 上で消すだけでは戻ることがある**：予約ファイルは git で管理しているので、commit・push までしないと、他の作業の git 操作でファイルが戻り、また登録されます。
- **取り込みが止まることがある**：消したファイルがリモート側で改稿されると、取り込み処理の `git pull` が失敗し、新しい予約まで入らなくなります。
- **画面から直接 push するのは不安定**：通信や、同じ作業フォルダを使う他のセッションとの競合で失敗すると、削除の操作そのものがエラーになります。取り込み処理ならもともと git を扱っていて、失敗はメールで通知され、次の回にやり直せます。

## この形にした場合に変わること
- **原稿が最新の状態から消えます**：削除した投稿の原稿はリポジトリの最新版から無くなります（git の履歴からは取り出せます）。
- **VPS から master への自動 commit が増えます**：削除のたびに「予約ファイルを削除」という commit が入ります。定期処理が自動で commit する例は、いまのところ他にありません。
- **対象は予約ファイルから登録された予約だけ**：画面で直接作った予約は、これまでどおり DB から消えるだけです。

## 変更するファイル
- `postcal/app.py`：削除時に「削除済み」を記録します。
- `scripts/postcal_import.py`：削除済みを登録し直さず、ファイルを消して commit・push します。

この形で実装してよいですか？ 実装後に、いま復活している 4 件（#32・#30・#31・#27）を画面でもう一度削除すれば、予約ファイルごと消えます。

### Claude *(22:22 JST)*

*[ツール: `Bash`]*

その形だと復活の問題は確かに無くなりますが、別の運用が 2 つ壊れるので、おすすめしません。前回の案（画面で削除した予約のファイルだけを消す）のほうが安全です。

## 壊れる運用
- **予約ファイルの改稿**：取り込み後も、下書きの間は予約ファイルを書き換えると画面に反映されます。この書き換えは直近だけで 8 回使われています（LRD が 3 回、ガリレオが 2 回、販促が 2 回、STS-51-F が 1 回）。取り込みは 10 分ごとなので、登録直後に消すと、改稿しようとした時点でファイルがもうありません。書き換えた側の push が「消されたファイルの変更」として衝突するか、別の予約として二重に登録されます。
- **販促の重複チェック**：`writer-xpromo` は `outputs/scheduled-posts/w007/` の予約ファイルを読んで、未投稿の予約と同じ記事や、過去と同じ切り口を避けています。ファイルが無くなると何も見つからず、同じ記事の販促をもう一度作ることがあります。

## ほかに変わること
- **チェックの記録が見えなくなる**：予約ファイルの「## 記録」は DB に入らないので、最新の状態からは無くなります（git の履歴には残ります）。
- **自動 commit が増える**：投稿 1 本ごとに「作成」と「削除」の 2 つの commit が master に入ります。

## おすすめ
前回の案のままがよいと考えます。予約ファイルは下書きの間だけ意味があるので、画面で削除したときにだけ消せば、改稿も重複チェックもそのまま使えます。

フォルダにファイルが溜まるのが気になる場合は、「投稿済みになった予約のファイルも消す」を足せます。その場合は `writer-xpromo` が投稿済みの予約ファイルを読む箇所を、outputs シートを読む形に直す必要があります。

前回の案で実装してよいですか？ 投稿済みのファイルも消す形にするかどうかも、あわせて教えてください。

## 私の判断で決めた点

- **削除のあとに予約ファイルが書き換えられていた場合は、消さずに新しい下書きとして登録します。** 削除直後に依頼した改稿が、黙って消えるのを避けるためです。不要ならもう一度削除すれば、ファイルも消えます。
- **push できなかったときは元に戻して、次回やり直します。** 30 分続いたらメールで知らせます。その間も下書きは復活しません。
- **VPS に未 push のコミットがある間は、ファイルの削除を見送ります。** 他のセッションのコミットを一緒に push しないためです。
- **投稿済みの予約と、その予約ファイルは消えません。** 追加案（投稿済みのファイルも消す）は入れていません。
- **同じ uid の予約ファイルをあとで作り直した場合は、新規として登録されます。**
