## 入力モード（2パターン）

起動時に冒頭で1回どちらかを確認する（**回答を待ってから制作に入る**）。ユーザーが原稿や URL を最初から渡している場合は確認不要でモードBとする。

- **モードA（newsTopics から選ぶ）**: `newsTopics` シート（SS1: `1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM`, `newsTopics!A:Z`）の G列（ステータス）が「未使用」の行から1件選ぶ。`/writer-xnews` の選定観点（驚き・「ポイント」欄の角度・カテゴリ「インパクト強め」優先・専門用語の少なさ）に従う。選定したネタの No と行番号を記憶する。
- **モードB（原稿・URL を渡す）**: ユーザーが渡した原稿・記事 URL・メモを題材にする。URL は WebFetch で取得する。**渡された内容に無い事実を新たに作らない**（事実の確認はフロー4 で行う）。

## Output (保存先)

```
（空。文面は書かない）
```


## Rules

### 制作フロー

1. **モード判定**: 入力モード（A/B）を確定する。ユーザーが原稿・URL を渡していればモードB。
2. **題材の確定**
   - **モードA**: 上記のとおり newsTopics から1件選ぶ。ネタの No・選んだ理由・「刺さるポイント」を1〜2行で示す。
   - **モードB**: 渡された原稿・URL から、ニュースの核心（誰が・何を・いつ）と「一番驚ける角度」を確定する。
3. **投稿フォルダ作成**: `projects/w005/YYYYMMDD_[topic]/` を作成し、`draft/`・`output/` を用意する。
4. **notebook の準備とニュースの事実確認（執筆前）**: `/research_setup-sources` を題材のテーマ（ニュースの主題＋ミッション名等）で実行し、NotebookLM の notebook を作成、公式プレスリリース等の一次情報をソースに追加する。返ってきた notebook_id を `notebook-id.md` に1行で保存する。本文作成・ファクトチェックは**この notebook のソースだけ**を根拠にする（ソースに無い事実は創作しない）。あわせて題材のニュースの**発表日・発表元・数値・固有名詞**を、公式プレスリリース等の一次情報で WebSearch / WebFetch により確認し、`draft/check-results.md` の冒頭に「## 事実メモ」として残す（項目ごとに出典 URL）。一次情報が見つからない項目は「未確認」と明記し、本文では使わないか、確認できた範囲の言い方にする。**ニュースが古い（発表から1週間以上）場合は、ユーザーに警告して続行を確認する**（速報性が価値のため）。
5. **本文作成**: `/writer-xpost` を呼ぶ。引数は次の形式。
   ```
   テーマ: {題材の1行要約＋選んだ角度}
   文字数: 500〜700字
   ```
   - 作業フォルダは投稿フォルダの親（`projects/w005/`）。`spec.md`・`plan.md`・`brand.md` を読ませる。
   - `writer-xpost` は「フォーカス3候補→決定／フック全型×3案→決定／可視ブロック設計（折り返し制約があるため実行される）→本文」を全自動で行う。出力を `draft/focus-candidates.md`・`draft/hook-candidates.md`・`draft/draft.md` に分けて保存する。
   - **字数の調整は「削除」で行う**（W001 spec フロー5.7 と同じ。段落・文を丸ごと落とし、残った文には手を入れない。執筆中は字数を見ない）。
   - **可視ブロック（先頭 280 weight）は `python3 ../../scripts/x_fold_split.py <本文ファイル>` で確認し、切れ位置が文の切れ目・謎や数字の直後になるようにする。** 可視ブロックを先に固定し、本文を足した後にもう一度確認する。
6. **チェック（以下の順で1ステップずつ実行する。同時に走らせない）**
   各ステップの結果は `draft/check-results.md` に追記する。
   1. **`/check-reader plan.md {本文}`**（素朴な読者）: 疑問・誤解・フック未回収を列挙し、本文に反映する。指摘が出なくなるまで最大3ループ。
   2. **`/check-fact-lim <notebook_id> {本文}`**（notebook ソース限定のファクトチェック。ID は `notebook-id.md`）: 明確な事実誤りを反映する。**抽出対象に「本文が前提として置いている一般論・比較の基準」を含める。** 劇的なディテール（人数・時間帯・具体的な数量）は一次資料で裏が取れるものだけを使う。最大5ループ。
   3. **`/check-critic --field {分野} {本文}`**（知識ある読者）: 指摘を `/check-fact-lim` で**裏取りしてから**反映する（裏取りなしで反映しない）。入れない論点は提示時に添える。最大3ループ。
   4. **`/check-yohn {本文}`**（よーん役最終検品。W005 専用ペルソナは未作成のため共通コアで検品する）: 指摘が出なくなるまで最大3ループ。
7. **ユーザー確認・承認**: チェックを反映した本文をユーザーに提示し、修正・承認を得る（**回答を待つ**）。
8. **ブランド適合チェック**: `/check-brand ../w001/brand.md {本文}`（W005 の `brand.md` は W001 を継承する差分のため、採点基準は W001 の `brand.md` を渡す）。全項目8点以上になるまで書き直し（最大5ループ）、合格本文をトンマナ調整する。事実は変えない。
9. **最終 reader（提示のみ）**: `/check-reader plan.md {本文}` を **1回だけ**実行する。**修正・ループはしない。** 出た指摘は `draft/check-results.md` に残し、ステップ10 の提示に添えるだけにする。
10. **ユーザーへ最終提示**: ブランドチェック済みの本文と、ステップ9 の指摘を併せて提示する。ユーザーが指摘を採用して修正した場合は、事実に関わる変更があれば `/check-fact-lim` を再実行する。
11. **添付画像（Web 検索）**: 題材に合う公式画像を WebSearch / WebFetch で探して `output/thumbnail.png`（または `.jpg`）として保存する。
    - 取得元は NASA/ESA/JAXA 等の**公式サイト・ニュースリリース**を優先する。**題材のニュースと画像の対象・年代・機体が一致するか確認する。**
    - 取得元 URL・ライセンス・公開日・用途を `output/image-source.md` に記録する。出典の明記が必要なら本編末尾に「画像: ○○」を置く。
    - **画像の内容が本編の結末や答えを先に見せていないか**（引きを殺さないか）を確認する。
    - 適切な公式画像が見つからないときは、ユーザーに報告して指示を待つ（生成画像で代用しない）。
12. **保存**: 本編・セルフリプ（空）・ハッシュタグを `output/index.md` に保存する。
13. **ネタのステータス更新（モードAのみ）**: 使用した newsTopics の G列を「使用済み」に更新する（`sheets_update_values`、`newsTopics!G{行番号}`）。
14. **X投稿用メール下書き作成**: W001 と同じ経路（`scripts/post_from_email.sh` が件名キーワードで未処理メールを検索し、`[投稿文]…[/投稿文]` と添付画像を投稿する）を使う。**件名は `【X科学ニュース】`（W005 専用）。**
    - 本文を一時ファイルに書き出す：
      ```
      [投稿文]
      （本編。末尾ハッシュタグ込み）
      [/投稿文]

      [リプ]
      [/リプ]
      ```
      `[リプ]` は**空のタグだけ**を入れる（cron は空なら本体のみを投稿し、リプは投稿しない）。`[note_url]` ブロックは入れない。
    - 投稿フォルダに `cd` してから `scripts/create_gmail_draft.sh` で作成する（gws の `--attach` はカレントディレクトリ内のファイルのみ）：
      ```bash
      cd {投稿フォルダ}
      bash $(git rev-parse --show-toplevel)/scripts/create_gmail_draft.sh \
        --to useakat@gmail.com \
        --subject "【X科学ニュース】$(TZ=Asia/Tokyo date '+%Y%m%d %H:%M:%S') の原稿ができました" \
        --body-file /tmp/w005_xnews_body.txt \
        --attach output/thumbnail.png
      ```
    - 成功判定は `✓ 下書き作成完了 (id: …)`。gws が認証エラーの場合は `scripts/gws_auth.sh` で再認証する。
    - 投稿時間帯は W001 と同じく、よーんが Gmail ラベル（`6時投稿` / `12時投稿` / `17時投稿` / `20時投稿`）を付けて指定する（任意。生成側は付けない）。
    - **自動投稿の cron 配線**: 未配線（2026-11-07 に一旦取り消し。当面は手動投稿）。配線する場合は `scripts/run_xlong_post.sh`（17:00 枠）と `scripts/post_by_label.sh` に件名 `【X科学ニュース】`(W005, ログ `x_post_xnews.log`) を追加する。
14.5. **フック型の記録**: `draft/hook-candidates.md` の「## 決定」で採用した型を `logs/hook_records.csv` に1行追記する。形式は W001 spec フロー14.5 と同じ（`日付(JST),W005,{①〜⑤+短縮名},{本編の冒頭15字},{モードとネタ 例:newsTopics[3]},,{謎},{自分事}`）。追記は投稿フォルダの通常コミットに含める。
15. **outputs シートへの記録**: 投稿が確定したら `outputs` シート（SS2: `1LerdRNS7dwPXhjunDY4Z4u7g7LWkQqABsat3_LBeIGc`）に what_id `W005` で記録する（列構成は既存の W001 行に合わせる。`note_url` は空）。
16. **投稿フォルダを Drive へアップロード**: `bash scripts/drive_put_folder.sh projects/w005/YYYYMMDD_[topic] 1m7ygvslsr50EbvWG7o74Pvq7soxYNnuz`（Drive の W005 用フォルダ）でアップロードする。
