# Production Spec — 困難を乗り越え成功した執念の物語の note 記事（W002）

> **共通ルール**：draft ファイルの扱い（`draft.md` を上書きで推敲する・初稿は `draft/first-draft.md` に自動凍結される）は `../CLAUDE.md` を参照。w001/w002/w003 で共通。

## Media (生成する媒体)
- note 記事本文（Markdown、**6000〜8000字**／有料 980円想定。6000字を下限、8000字を上限の目安とする）
- 各 H2 セクションの画像プロンプト（テキストで提案。実画像生成はスキルに委ねる）


## Input (読み込むファイル)
- `../../plan.md`（共通の発信目的・ターゲット）
- `../../brand.md`（共通ブランド定義）
- `plan.md`（本プロジェクトの目的・ターゲット）
- `brand.md`（本プロジェクトの表現ルール・文体・演出ルール）
- `reference/articles/`（過去記事 mhtml）／`reference/thumbnails/`（サムネイル参考画像）／`reference/markdown-rules.md`（Markdown 表記ルール）
- Google Sheets `noteNeta`（spreadSheet ID: `1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM`）— ネタ在庫（L列ステータス「未使用」のみ対象。**モードA のみ**）
- **（モードB のみ）ソースとなる X長文ポストフォルダ**: `../../w001/<YYYYMMDD_テーマ>/`
  - `notebook-id.md`（再利用する NotebookLM notebook ID）
  - `output/index.md`（深掘り元となる X長文本文）
  - ※ `neta-id.md` は読まない（ネタ番号の確認・継承はしない）

### 画像・生成プロンプト案

* 画像種類：図解 / イメージ / 写真
* 図解・イメージとも `/lovart` スキル（Lovart AI）で生成する。参照画像がある場合は `upload` で CDN に上げて `--attachments` で渡す。写真案はスキップ。

### 公開原稿
`YYYY-MM-DD_<短いタイトル>/output/index.md`

### 参考情報の書式（2段階運用）
何を出典として付けるか（史実・数値・科学的知見）と、捏造しない原則は brand.md「史実・出典」を参照。本文末尾に `## 参考情報` を置き、以下の書式で運用する。

- **下書き（draft.md）＝出典マーカー＋「本文での参照内容」**（ファクトチェック用）
  - 該当記述に `[N]` を付ける。`[N]` の前は半角スペース。番号は句読点の前。複数は `[1,2]` 昇順。
  - `## 参考情報` の各項目に「本文がその資料から採った内容（事実の要約。必要なら原文引用）」を添える。形式：`1. [著者・タイトル・媒体・年](URL) — 本文での参照内容`。
- **公開版（output/index.md）＝マーカーを外し「文献の概要」**（読み物として軽くする）
  - 本文の `[N]` マーカーはすべて削除する。
  - `## 参考情報` の各項目に「その文献自体の概要（何を扱った資料か）」を添える。本文での参照内容（draft 側のメモ）は書かない。形式：`1. [著者・タイトル・媒体・年](URL) — 文献の概要`。
- URL は必須（DOI があれば優先。リンク先が開けること）。

### 画像・生成プロンプト
- プロンプト: `YYYY-MM-DD_<短いタイトル>/output/images/<H2セクションタイトル>_<画像種類>.md`
- 画像: `YYYY-MM-DD_<短いタイトル>/output/images/<H2セクションタイトル>_<画像種類>.png`

### サムネイル
作業フォルダ: `YYYY-MM-DD_<短いタイトル>/thumbnail/`
- `plan.md` … 目的・ターゲット・要件・KPI・納品物・失格条件
- `brand.md` … サムネのトーン・ビジュアル指針（記事 brand を継承）
- `design-brief_template.md`（指示書テンプレ）／`design-brief.md`（記事ごとの指示書）
- `nanobanana-prompt.md` … 画像生成プロンプト
完成画像: `YYYY-MM-DD_<短いタイトル>/output/images/thumbnail.png`（**1280×672px**）

* `plan.md`／`brand.md`／`design-brief_template.md` は雛形を流用する（無ければ既存記事の `thumbnail/` からコピー）。


## Rules

### 制作フロー

**冒頭でモードを判定する。**
- **モードA（ネタ起点・新規）**: `noteNeta` の未使用ネタから新規に note 記事を作る（従来フロー）
- **モードB（X深掘り）**: 既存の X長文ポスト（w001）のテーマを深掘りして有料 note 記事にする
- **モードC（協調／ブリーフ起点）**: `/plan-xnote-funnel` が作った分割設計ブリーフ `funnel-brief.md` を起点に、X長文と一体で設計された有料 note を作る（**note を先に仕上げ・公開 → 後で W001 X長文を投稿**する導線前提）
- ※ ユーザーが `funnel-brief.md`（分割設計ブリーフ）を指定したら**モードC**。w001 配下の X投稿フォルダを指定したら**モードB**。指定がなければ**モードA**。

各モードの導入ステップを実施したのち、**共通フロー（ステップ6以降）に合流する**。

#### 【モードA：導入】
A1. **ネタ選定** — `noteNeta` シートで L列「未使用」のネタから選ぶ（ユーザー指定時も未使用を確認）
A2. **記事フォルダの作成** — `YYYY-MM-DD_<短いタイトル>`という名前のフォルダを作成する。作成する記事に関するファイルはこのフォルダの中に格納する。
A3. **関連情報リサーチ** — research_setup-sources スキルを使い、notebookLM の notebook を作成し、ネタに関連する信頼度の高い情報源をソースとして追加する。スキルが出力する <notebook ID> は `notebook-id.md` に保存しておく。以下のステップ A4〜A5 は、notebook のソースの情報だけをもとに行う。
A4. **参考情報の確認** — `reference/articles/` フォルダにある過去の記事例（mhtml）を読み込む
A5. **構成フェーズ** — タイトル案10個とその中の推奨案を1つ・狙い・想定読者・構成案・文字配分を提示し、**ユーザー承認を待つ**（承認前に本文を書かない）。この内容は `draft/agenda.md` に保存しておく。

#### 【モードB：導入】（X深掘り）
B1. **ソース投稿の特定** — ユーザー指定の w001 内 X長文ポストフォルダを特定する（曖昧なら確認する）。
B2. **notebook 特定** — そのフォルダの `notebook-id.md` の notebook を再利用する（※ ネタ番号の確認は行わない）。
B3. **記事フォルダの作成** — w002 に `YYYY-MM-DD_<短いタイトル>/` を作成する。`<短いタイトル>` は元の X長文ポストフォルダ名（日付以降）と同じにする。`notebook-id.md` に w001 の ID を継承コピーし、`source-x-post.md` に元フォルダの相対パスを記録する。
B4. **参考情報の確認** — `reference/articles/` フォルダにある過去の記事例（mhtml）を読み、文体・構成傾向を把握する。
B5. **構成案提案【対話①】** — `output/index.md`（X長文本文）を notebook に渡し、「この投稿をふくらませて **6000〜8000字・980円有料** note 記事にする構成案を、notebook のソースを根拠に**5案**」提案させる → **ユーザーが1案を決定**。
    - 問い合わせは `python3 $(git rev-parse --show-toplevel)/scripts/notebooklm_manager.py ask <notebook_id> "<質問>"` を使う。X本文と「6000-8000字・980円有料・ふくらませる方向」を質問文に同梱する（X本文はソース追加せず prompt に埋め込む）。
B6. **タイトル案【対話②】** — 決定した構成案をもとにタイトル案を**5つ**提示する → **ユーザーが決定**。
B7. **文字配分込み構成【対話③】** — 決定タイトル＋構成案をもとに、狙い・想定読者・構成案・各H2の文字配分を提示し、**ユーザー承認を待つ**（承認前に本文を書かない）。この内容は `draft/agenda.md` に保存しておく。

#### 【モードC：導入】（協調／ブリーフ起点）
C1. **ブリーフの特定** — ユーザー指定の分割設計ブリーフ `funnel-brief.md` を特定する（通常 `projects/w002/<YYYY-MM-DD_短いタイトル>/draft/funnel-brief.md`）。曖昧なら確認する。
C2. **記事フォルダ・notebook** — ブリーフが置かれたフォルダ（`draft/` の親）をそのまま記事フォルダとして使う。ブリーフの `notebook_id` を `notebook-id.md` に書き込み継承する（X長文と同じ根拠）。
C3. **参考情報の確認** — `reference/articles/` の過去記事例（mhtml）を読み、文体・構成傾向を把握する。
C4. **構成案【対話①】** — **B5 の「独立5構成案」の代わりに、ブリーフの「note の売り／課金壁の位置イメージ」から構成案を導く**。有料部分にブリーフの“売り”（クライマックスの詳細・種明かし・独自資料/証言/年表・意味の宣言）が入るように組み、無料部分（冒頭〜課金壁）を設計する。**note は X長文と独立した完結記事**として書くため、**X の既出範囲を無料部分で再掲してよい**（温存すべきは有料部分の売り）。構成案を提示し **ユーザーが決定**。
C5. **タイトル案【対話②】** — B6 と同じ（5案提示 → ユーザー決定）。ブリーフのタイトル案があれば起点にする。
C6. **文字配分込み構成【対話③】** — B7 と同じ（狙い・想定読者・構成案・各H2の文字配分を提示 → **承認を待つ**）。`draft/agenda.md` に保存。
C7. **ブリーフ整合** — 制作した note の“売り”がブリーフの `## note の売り` と一致していること、セルフリプ文面（`## セルフリプ`）が有料部分の売りを正しく予告していることを確認する（ズレがあればブリーフ側と擦り合わせる）。

#### 【構成フェーズ共通ルール（A5・B7・C6 に適用）】
`draft/agenda.md` には構成案・文字配分に加えて、以下の2つを必ず含めてからユーザー承認を得る（ケプラー記事 2026-08 で、これらの判断が執筆後に起きて大改稿になった再発防止）。

- **難所マップ**: まず `/check-reader --plan ../plan.md {タイトル＋構成案}` を実行し（`../plan.md` ＝ w002 の `plan.md`。Audience セクションが読者ペルソナ）、**plan.md の想定読者ペルソナになりきった読者役エージェント**に構成案を読ませて「章ごとの疑問・期待する種明かし・難所の予感」を列挙させる（書き手が自分で難所を挙げるのは知識の呪いで漏れるため、必ず読者役に出させる）。返ってきた疑問リストの各項目について、writer が扱いを **本編で解く／付録に送る／断言で流す** から決めて agenda に明記する。**主筋を止めるが省くと論理が飛ぶ説明は「付録」H2 に切り出してよい**（付録は記事末尾・参考情報の前。文字数はH2配分に含めて計上する）。
- **H2統合チェック**: 文字配分が **600字未満のH2は隣接H2との統合を検討**し、分けたまま残す場合は理由を添える（薄い章は書くと重複が生じやすい。ブリーフ・構成案のH2割りをそのまま採用しない）。
- **agenda の導入欄はテーマ宣言（設計図）であって、導入の文言そのものではない**: 導入欄に書くズラシ・テーマ宣言（例：「オポチュニティを殺したのも、生かしたのも、同じものだった」）は記事全体の設計図であり、そのまま本文の導入に書くと核心を先に明かす種明かしになる（オポチュニティ記事の制作で実際に起きた）。本文の導入で書くのは、このテーマへ向かう**問い**であって、答えではない。

#### 【共通フロー（本文以降）】
6. **本文フェーズ**: 承認済み構成を厳守して執筆する。**本文はスキルに委譲せず、担当エージェントが `brand.md`（文体・演出ルール）に沿って直接（インライン）執筆する**（`writer_note-story` は旧系統で、出典マーカー `[^N]`・URL 省略可・下流フローが本フローと異なるため使わない）。**技術・仕組みの説明（装置の動作・因果）は、書く前に notebook で仕組みを確定してから書く**（CLAUDE.md「リサーチ運用ルール」）。※ モードB では、事実が不足する場合のみ、リサーチ運用ルール（重複確認のうえ）に従い notebook にソースを追加する。
   - **事実の採用マーク（書く前）**: funnel-brief の深掘りメモ・notebook の事実は「使える在庫」であり「使うべきリスト」ではない。執筆前に使う事実だけを選び、**「この事実は主筋（執念の物語）にどう効くか」を1行で書けたものだけ採用**する。書けない技術詳細・固有名・脇道の経緯は最初から書かない（書いてから削るのは、削る判断も改稿も高くつく）。
   - **読者疑問への回答割り付け（書く前）**: agenda の難所マップ（`/check-reader --plan` の読者疑問リスト＋writer の扱い決定）を開き、「本編で解く」とした疑問それぞれに、どの段落で答えるかを割り付けてから書く。見かけの矛盾は、**読者の疑問をセリフで先に立ててから答える**形が有効（例:「ちょっと待って。実証テストで5%以内と出たばかりでは？」）。
   - **図番号は本文の登場順に採番**する（【図N：説明】プレースホルダ）。funnel-brief・image-plan の図番号が登場順と食い違う場合は、本文側で振り直す。
   - **導入の種明かし照合（書いたら）**: 導入を書いたら、難所マップの「読者の疑問・期待する種明かし」リストと照合し、その答えを導入が先に言っていないか確認する。該当していたら、①抽象度を1段上げる（具体的な仕組み・固有名→一般的な言葉）か、②疑問形に変換する、のいずれかで書き直す（brand.md「導入で使わない表現」参照）。
7. **6000〜8000字チェック**: 6000字未満なら不足セクションを加筆し再カウント。8000字を超える場合は冗長部を圧縮する。**セクション別の実文字数と agenda 目標の比較表を python で作成してユーザーに提示する**（目標から大きく乖離するセクションは理由を添える。特定セクションだけ膨らむと他の薄さが目立つため、全体バランスをここで可視化する）。
   - **加筆は水増ししない。** 冗長な前置き・中身のない強調語・同義の言い換えで字数を稼がない（brand.md「Do Not」準拠）。
   - 目標に届かない分は、**公開ソースで裏が取れる「別の具体」（新しい事実・数値・固有名・経緯・当事者の発言）を足して**埋める。書く前に notebook／WebSearch・WebFetch で裏取りする。
   - 源のある具体が見つからない章（導入フック・解釈中心の章など）は、無理に目標値まで埋めず、密度より切れ味を優先してよい。**何を足さず据え置いたかを一言添えて報告する。**
8. **演出＋読者視点セルフチェック（2周する）**:
   - **1周目（構造・出典）**: 導入H2なし／各H2末尾`---`／H3なし／専門語の噛み砕き／各H2に演出装置／`[N]`形式／brand.md「出力前セルフチェック」の全項目 を確認する。引用番号の整合（本文の `[N]` と `## 参考情報` の番号の過不足）は python で機械チェックする。
   - **2周目（初読の読者になりきる通し読み）**: 1周目とは別の回で、初めて読む読者の目で全文を通し読みし、以下を自分で直す：①依存順序（用語を使う前に前提を説明済みか・前方参照がないか）②過剰断定（「すべて／必ず／〜寸前」等が事実・出典の範囲を超えていないか）③呼称の揺れ・装置の帰属（ロケット／宇宙船／機体の統一）④強い主張・仕組みの記述は notebook／原文で裏取り済みか ⑤読者の即時疑問（動力・位置・因果）に先回りできているか（brand.md「論理の橋」）
   - ※1周では取り切れない指摘が2周目で出るのが常のため、省略しない。
9. **ファクトチェック**: `/check-fact-lim <notebook_id>`（`notebook-id.md` の ID。notebook のソースのみを根拠にする。最大5回ループ）。指摘を反映した版を最終本文とする
9.5. **知識ある読者チェック**: `/check-critic --field {分野} {本文}` を実行する。知識ある読者役が、事実への反論・単純化しすぎ・**本文が触れていない前提への疑問**・論理の穴を列挙する。**各指摘を notebook（`/check-fact-lim` への照会）で裏取り**し、事実誤りは修正、本文を強める論点は反映、入れない論点は付録 H2 への追加候補としてユーザーに提示する。指摘を裏取りなしで反映しない。
10. **参考情報チェック**: draft.md の参考情報リスト（`## 参考情報`）の各文献について以下を実施する
    1. NotebookLM の notebook（notebook-id.md に記載の ID）に「各参考情報について、本文が参照した内容を根拠ソース・該当記述付きで確認してください」と問い合わせる
