# Production Spec — X 短文投稿（Z01）

## Media (生成する媒体)
- X 投稿テキスト（**140 字テキストのみ**。画像なし）

## Input (読み込むファイル)
- `../../plan.md`
- `../../brand.md`（共通ブランド定義）
- `plan.md`（本プロジェクトの目的・ターゲット）
- `brand.md`（本プロジェクトの表現ルール）
- Google Sheets SS1（spreadsheetId: `1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM`）のネタプール
  - **選定対象: `noteNeta` / `newsTopics`**（1:1、`onePointNeta` / `thoughts` は選定対象外）
  - `noteNeta` / `newsTopics` はどちらも投稿文を生成する通常フロー

## Output (保存先)
- **予約ファイル（Markdown）**：確定稿を `outputs/scheduled-posts/z01/<YYYYMMDD_HHMMSS>_<topic>.md` に書き、`git` で master へ push する。**Gmail 下書きは作らない。**
- VPS の `scripts/postcal_import.py`（systemd timer・10 分ごと）がこの予約ファイルを読み、**下書き（draft）として** postcal に登録する（仮の日時は週間スケジュールの最寄りの空き短文枠）。下書きは `post.usephys.net`（postcal カレンダー）に「下書き（未予約）」と表示され、**この時点では投稿されない**。**よーんが画面で本文を確認・修正し「投稿予約」を押すと予約（queued）になり**、既存の 4 枠 cron がその枠で X / Threads に投稿する（2026-11-21〜）。
- **本フローでは投稿は一切行わない**（X 投稿は cron 定時実行のみ）。予約ファイルが唯一のローカル成果物（記録）。

## Format
- **テキスト**: 常体（だ／のだ調）、3 パート構成（フック→核心→締め。`brand.md` 参照）。
- **文字数**: 厳密に **135〜140 字**（改行・空白を含む総文字数）。
- ハッシュタグ・絵文字・CTA・画像なし。

## Naming

### 予約ファイル（Markdown）
- パス: `outputs/scheduled-posts/z01/<YYYYMMDD_HHMMSS>_<topicスラッグ>.md`（JST。topic は投稿文の核心キーワードを 10〜15 字の名詞句で、ファイル名用に空白は `_`・記号は除去）。
- **枠（日付・時刻）は本フローでは決めない。** VPS の `postcal_import.py` が front-matter の `uid` をキーに、週間スケジュールの短文枠で「今日以降の最も近い空き枠」を選んで登録する。
  - 週間短文枠（よーん決定 2026-11-19）: 1 短文の日は 6:00、2 短文の日は 6:00→17:00。月[6] 火[6,17] 水[6] 木[6,17] 金[なし] 土[6] 日[6]
- **構成**: `## 投稿文` / `## セルフリプ` / `## 記録` の 3 つだけを `##`（レベル 2）見出しにする。記録内の小見出しは `###` を使う（インポーターが `## 投稿文`・`## セルフリプ`・`## 記録` の位置でセクションを切り出すため、本文側にレベル 2 見出しを混ぜない）。

```md
---
uid: <初回に生成した 32 桁 hex・以降固定>
project: z01
what_id: z01
kind: short
threads_enabled: true
note_url: ""
source: "{ソースシート}[{ネタ番号}]"
session_url: "{この原稿を作ったセッションの URL。無ければ空文字}"
topic: "{トピック要約 10〜15 字}"
created: "YYYY-MM-DD HH:MM:SS JST"
---

## 投稿文

{確定稿（135〜140 字）だけ。他の行を混ぜない}

## セルフリプ

なし

## 記録

### ソース
{ソースシート}[{ネタ番号}]

### フォーカス候補
{/writer-xpost のフォーカス3候補＋「決定」}

### 冒頭フック候補
{hook-patterns.md の全型 × 各型3案を型別見出し付きで全列挙＋「決定」}

### 締め候補
{brand.md「締めの作り方」の5型それぞれの候補＋「決定」と選んだ理由}
```

- **`session_url`**：この原稿を作った Claude セッションの URL（`https://claude.ai/code/session_…`）。システムの commit 署名指示にある `Claude-Session:` の URL をそのまま使う。postcal の画面（下書きの編集画面・一覧）に「このセッションを開く」リンクとして出て、よーんが修正を頼むときにすぐ開ける。**URL が分からない（ローカル実行などで `Claude-Session:` が無い）ときは空文字にする（推測で書かない）。** インポーターは `https://claude.ai/code/…` の形だけを採用する。
- **`## 投稿文` には確定稿だけを置く**（`postcal_import.py` がこのセクションを投稿本文として抽出する）。セルフリプが無ければ `## セルフリプ` の中身は「なし」。
- **`## 記録` に check 証跡・候補を全部残す**（これが Gmail 下書きに書いていた内容の保管先）。`### チェック証跡` の各行は、該当 `/check-*` を「実起動した」結果を書く（STEP 3.7 / 4 / 4.5 / 5 / 5.5）。実起動していない工程は空欄にせず、未実行＝違反。各行にループ回数と収束/未収束を必ず記す。

## Rules

### 制作フロー（この spec.md を正として実行する。`/writer-xshort` スキルは廃止予定で使わない）

> **【フロー順守の鉄則】STEP 3〜6 は、ここに書かれた順序で1回ずつ実行する。spec に無い手順（工程の追加・前工程への往復・やり直しループ）を勝手に挟まない。**
> - 各チェックは定義された位置でだけ動かす：**check-reader は STEP 3.7（主責任。ここで収束させきる）と、後工程で本文の中身が変わった場合のみ STEP 5.6 の最終1パス**、**check-critic は STEP 4.5 のみ**（ここで収束させきる）、**check-yohn は STEP 5.5 のみ**。各チェックのループ（指摘がなくなる or 最大回数）はその STEP の中で閉じる。最大回数は reader 3（＋5.6 の最終1パス）・fact 5・critic 3・brand 5・yohn 3。
> - **各 `/check-*`（check-reader / check-fact / check-critic / check-brand / check-yohn）は Skill または Agent として実起動する。自己検品・インラインでの代替、および「◯◯相当の自己検品」等の表現による工程スキップは禁止。** 実起動しなければ下記 Naming の `[チェック証跡]` に埋める各役の結果が存在しないため、証跡が空＝未実行（違反）として扱う。
> - 由来：2026-10-22 ローマン望遠鏡。逆説フック「広く撮れば画質は落ちる」の前提（画素数が一定のとき）の見落としを、check-critic を実起動せず「check-critic 相当の自己検品」で済ませたことが通した逸脱の再発防止。
> - **check-yohn（5.5）を通過したら、STEP 5.6（後工程で本文が変わった場合のみ最終 reader 1パス）→ 5.7 ゲート → 6 予約ファイル作成 → 完了報告へ進む。** reader の主責任は 3.7。ただし後工程（fact/critic/brand/yohn）で本文の中身が変わった場合に限り、確定ゲート直前の STEP 5.6 で最終稿に reader を1パスだけかける（**1パスのみ。出た指摘は修正せず完了報告に提示する**。3.7 へ往復はしない）。これ以外の前工程への差し戻し・spec に無い自作ループは禁止（ガリレオ逸脱＝どのチェックも通らない自作版を出す事故の防止）。
> - 提示・予約にする本文は「**5.5 を通過し 5.7 の機械ゲートを満たした、その版そのもの**」とする。チェック後に本文を書き換えたら、その版は未検証なので**使わない**。**確定ゲート直前（5.6 以降）では本文を書き換えない**——5.6 の reader 指摘は修正せず完了報告に提示し、よーんの手直しにゆだねる（確定ゲート直前の改稿は未検証の版を予約に入れるため。2026-11-13 の事故）。
> - 由来：2026-10-01 ガリレオ。check-reader で Yes を得て check-yohn に進んだ後、spec に無い「check-yohn→check-reader」の往復を自作し、どのチェックも通っていない自作版を下書きにした逸脱の再発防止。

#### STEP 1: ソースシートをランダムに決定
SS1 の 2 シート（`noteNeta` / `newsTopics`）から、**1:1 で 1 シートをランダムに選ぶ**（`onePointNeta` / `thoughts` は選定対象外）：

```bash
python3 -c "import random; print(random.choice(['noteNeta','newsTopics']))"
```

- `onePointNeta` / `thoughts` を除外し、物語型（noteNeta）・ニュース（newsTopics）を 1:1 の割合で出す方針（2026-11-18 改定：thoughts 枠の空タグ下書きフローは廃止し、選定対象から外した）。
- どちらを選んでも **通常フロー**（STEP 2 → 2.7 → 3〜5.7 で投稿文を生成 → STEP 6 で予約ファイル作成 → 7）で進む。
- 選んだシート名を **【ソースシート】** として記憶する。

#### STEP 2: 選んだシートからランダムに 1 行を取得
1. 選んだシートのデータを取得する。範囲は次のとおり：

   | シート       | 取得範囲          | ID/No 列 | 使用する内容列                      | フィルタ列（ステータス／短文最終使用日） |
   |-------------|-------------------|----------|--------------------------------------|------------------------------------------|
   | noteNeta     | `noteNeta!A:N`     | A(No)    | B(タイトル案), E(危機の内容)        | L(ステータス) / N(短文最終使用日)         |
   | newsTopics   | `newsTopics!A:I`   | A(No)    | C(タイトル), D(概要), E(ポイント)   | G(ステータス) / I(短文最終使用日)         |

   ```
   sheets_get_values(spreadsheetId="1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM", range="{選んだシートの取得範囲}")
   ```

2. **候補行の絞り込み**（noteNeta / newsTopics に下記フィルタを適用する）：
   - ヘッダー行を除いた全データ行のうち、次の条件を**両方満たす行**を候補とする：
     1. フィルタ列の「ステータス」が **「ボツ」ではない**
     2. フィルタ列の「短文最終使用日」が **空、または今日から 6ヶ月（180日）以上前**（例: `python3 -c "from datetime import date, timedelta; print((date.today()-timedelta(days=180)).isoformat())"` で閾値日付を求め、文字列比較する）
   - **候補が 0 件の場合はネタ枯渇とみなす**。投稿文生成以降には進まず、STEP 7 で完了報告の代わりに枯渇報告を出して終了する（詳細は STEP 7 参照）。3 段階フォールバックなどは行わない。

3. 候補行の中から **ランダムに 1 行**を選ぶ：

   ```bash
   python3 -c "import random, sys; n=int(sys.argv[1]); print(random.randint(0, n-1))" {候補行数}
   ```

4. 選んだ行について以下を記憶する：
   - **【ネタ番号】**: 選択行の A 列値（No または ID）
   - **【ネタ内容】**: 選択行の主要テキスト（上表の「使用する内容列」を結合）

#### STEP 2.7: 重複トピック回避（`logs/hook_records.csv` 突合）
投稿文を作る前に、過去の投稿記録 `logs/hook_records.csv` と突合し、同じ題材・同じ主人公の使い回しを避ける。短文最終使用日フィルタ（ネタ番号単位）だけでは、別のネタ番号から同じ主人公・固有名が主役として繰り返し選ばれる取りこぼしが起きるため、この工程で**題材（主人公）レベルの重複**を止める（2026-09-28 に過去投稿と主人公が重複した事故を受けて追加。noteNeta / newsTopics 間の主人公重複を止める工程として継続する）。

1. `logs/hook_records.csv` を Read し、`プロジェクト` 列が **z01** の行のうち **今日から90日以内** の行を対象にする。各行の `冒頭15字`・`ソース` 列から、過去に投稿した題材・主人公を把握する。
2. **回避リストを作る**（題材・主人公＝探査機・宇宙船・ミッション名・人物・天体・固有の事件名など、投稿の主役になる固有名）：
   - 今回の【ネタ番号】と**同じ `ソース`**（例: `noteNeta[49]`）が過去90日にあれば、その行の題材・主人公（例: 「太陽観測衛星ステレオ」）を回避リストに入れる。
   - 加えて、z01 全体で **直近30日**に主役として使った主人公・固有名を回避リストに入れる。
3. 回避リストを STEP 3 に渡す。**STEP 3 のフォーカス決定では、回避リストにある題材・主人公を主役にしない。** 3つのフォーカス候補がすべて回避リストと衝突する場合は、別の主人公・切り口で候補を作り直す。
4. 3つのフォーカス候補が回避リストと衝突して別の主人公・切り口も作れない（出尽くしている）場合は、**STEP 1 に戻ってシートを選び直す（1回だけ）**。それでも重複しか作れない場合は、STEP 7 の完了報告に「重複回避不可」と明記したうえで進む。

通過後に STEP 3 へ進む。

#### STEP 3: 投稿文生成（`/writer-xpost` を使う）
投稿文の作成は `/writer-xpost` スキルに委ねる。**STEP 2.7 の回避リストにある題材・主人公は主役に選ばない**（衝突しないフォーカスを採用する）。**呼び出す前に `../../style/z01-phrasebook.md`（語彙の好み帳）を Read し、生成時に「好みの方向」に寄せ「避ける」列の表現を出さないようにする。** STEP 2 で選んだネタをテーマとして、文字数範囲 135〜140 字を指定して呼び出す：

```
/writer-xpost
テーマ: {STEP 2 の【ネタ内容】}
文字数: 135〜140字
```

- `/writer-xpost` は本作業フォルダ（z01）の `spec.md`・`plan.md`・`brand.md` を読み込み、投稿文を作成する。
- `/writer-xpost` の出力（フォーカス候補・冒頭フック候補・投稿内容）のうち、**投稿内容** を投稿文として採用する。本フローでは draft への保存は不要（予約ファイルが成果物のため、保存はスキップしてよい）。
- **フォーカス決定のとき、次の2つを必ず決める**（予約ファイルの `### フォーカス候補` に記録する）：
  - **驚き宣言（20字以内）**：この投稿で読者に渡す驚きを1つだけ、一言で言い切る。
  - **捨てる事実リスト**：ネタ元にあるが本文に入れない事実を列挙する。
  - 以降の全工程（推敲・チェック反映）で、捨てる事実リストの項目を本文に戻さない。チェックの指摘で必要になった場合は、リストを更新して記録に残す。
- **字数が下限（135字）に届かないときは、事実を足さず、主人公の動作・情景・日常接続で埋める。** 事実を足してよいのは、驚き宣言を支える場合に限る（`brand.md`「文字数」参照）。
- **締めの文は、型を分けて候補を作ってから選ぶ**（`brand.md`「締めの作り方」の5型と選定基準に従う。候補と決定を予約ファイルの `### 締め候補` に記録する）。
- 由来：2026-11-27 の newsTopics 制作。字数の下限を満たすためにネタ元の副次的事実を盛り込み、焦点がぼやけた。締めも事実の言い直しで余韻がなかった。

#### STEP 3.5: セルフ推敲（ファクトチェック前に必ず通す）
STEP 3 で採用した投稿文を、外部チェックに出す前に自分で推敲する：

1. **物語チェック**: `../../style/story-check.md` の7項目（時系列・行動とテーマの整合・接続詞の受け先・史実帰属・結末の完結・フックの回収・語の重複）を1つずつ点検し、該当箇所があれば書き直す。
2. **語彙チェック**: `../../style/z01-phrasebook.md` の「避ける」列に該当する表現が残っていないか点検し、あれば「好みの方向」に置き換える。
3. **字数再計測**: 1〜2 で修正したら実文字数を数え直し、135〜140 字に収まっていることを確認する（`python3 -c "print(len('''…'''))"`）。範囲外なら `brand.md` の削る対象優先度に従って収め直す。

通過後に STEP 3.7 へ進む。

#### STEP 3.7: 素朴な読者チェック（`/check-reader` を使う）
セルフ推敲を通過した投稿文を、制作文脈を知らない読者役エージェントに読ませ、読者の即時疑問を潰す：

```
/check-reader plan.md {STEP 3.5 通過後の投稿文}
```

- 読者役（PE01）が原稿だけを初見で読み、「何の？」「どうやって？」「なぜ？」の疑問・誤解した映像・フック未回収を列挙する。writer は疑問に**本文中で答える形**で改稿し、疑問が出なくなるまで最大3ループ回す（詳細は `/check-reader` スキル参照）。
- 改稿で字数が 135〜140 字から外れた場合は範囲内に収め直す。
- 由来: 2026-08-06 のテミス/アルテミス制作で、/check-fact・/check-brand を1発合格した原稿に読者視点の指摘だけで8往復の推敲が必要だった（「何の影？」「月面に置いたように読める」等）。書き手には見えない疑問を別コンテキストの読者役で検出する。

通過後に STEP 4 へ進む。

#### STEP 4: ファクトチェック（`/check-fact` を使う）
採用した投稿文を `/check-fact` でファクトチェックする（テキスト入力モード）：

```
/check-fact {STEP 3 で採用した投稿文}
```

- 明確な事実誤り（数値・固有名詞・年代・因果の誤り）があれば訂正を反映する。
- 訂正で字数が 135〜140 字から外れた場合は、`brand.md` の削る対象優先度に従って範囲内に収め直す。
- **一次情報主義**：距離・サイズ・年代などの数値は、プレス記事・二次情報の丸め値で確定しない。一次情報（論文・arXiv・公式）に遡り、赤方偏移からの距離のような換算が必要な値は計算して裏取りする（例: z→ルックバック/共動距離、Mpc→光年）。プレスの「about a billion light-years」等はオーダーを外すことがある。
- **編集後の再チェック**：`/check-fact` 通過後に**数値・固有名詞を1つでも追加・変更したら、その原稿で `/check-fact` を必ず再実行する**（チェックの網の外で新しい数値が混入する事故を防ぐ）。

通過後に STEP 4.5 へ進む。

#### STEP 4.5: 知識ある読者チェック（`/check-critic` を使う）
ファクトチェック済みの投稿文を、知識ある読者役エージェントに読ませ、突っ込みどころを検出する：

```
/check-critic --field {分野} {STEP 4 通過後の投稿文}
```

- 知識ある読者役が、事実への反論・単純化しすぎ・**本文が触れていない前提への疑問**・論理の穴を列挙する（詳細は `/check-critic` スキル参照）。

#### STEP 5.7: 確定ゲート（機械チェック。ここを通った本文が「確定稿」）
無人フローでは人の承認が取れないため、**「確定」＝ STEP 3.5〜5.5 の全チェック通過＋この STEP 5.7 合格**と定義する。STEP 5.5 通過後の本文に対し、次を機械的に検証する。1つでも不合格なら STEP 6 に進まず、該当箇所を直して STEP 5.7 を再実行する（数値・固有名詞を変えたら STEP 4 の再チェックルールに従う）:

1. **字数**: `python3 -c "print(len('''…'''))"` で **135〜140 字**（改行・空白を含む）
2. **禁止要素**: ハッシュタグ（`#`）・絵文字・「！」の多用・「——」・ですます語尾（です／ます／でしょう）が含まれていない
3. **見出し混入なし**: 確定稿（`## 投稿文` に入れる本文）に行頭 `## `（レベル2見出し）を含まない（`postcal_import.py` のセクション切り出しを壊さないため。135〜140 字の本文では通常問題ないが念のため確認）
4. **捨てる事実の混入なし**: STEP 3 で決めた「捨てる事実リスト」の各項目（数値・固有名詞・キーワード）が確定稿に含まれていない。リストの語を1つずつ本文と照合する（例: `python3 -c "t='''…'''; print([w for w in [{リストの語}] if w in t])"` が空リスト）。含まれていたら該当箇所を削り、字数は事実を足さずに埋め直す

ここで確定した本文だけを STEP 6 に渡し、**STEP 6 以降（提示まで）で本文を変更しない**（投稿前の修正は STEP 6 の更新ルールに従い、同じ予約ファイルを上書き更新する）。確定の精度は check-yohn の自己改善ループ（予約提示後の指摘をペルソナへ追記）で上げる。

通過後に STEP 6 へ進む。

#### STEP 6: 予約ファイルの作成と push（noteNeta / newsTopics の通常フロー）
Gmail 下書きは作らない。確定稿を**予約ファイル（Markdown）**として書き、hook 記録とともに master へ push する。VPS の `scripts/postcal_import.py`（systemd timer）がこれを読み、**下書き（draft）として**登録する（仮の日時は週間スケジュールの最寄りの空き短文枠。`post.usephys.net` に「下書き（未予約）」と表示される）。**下書きは投稿されない。よーんが画面で確認・修正して「投稿予約」を押すと予約になり、cron がその枠で X / Threads に投稿する。**

> **更新ルール（2026-11-21 改定：下書き方式）**：予約ファイルを上書き更新して再 push してよいのは、**postcal 上でまだ下書き（draft）の間だけ**。front-matter の `uid` は初回に 1 度だけ生成して固定し、修正時は**同じファイル（同じ uid）を上書き**する（インポーターが uid をキーに既存の下書きを更新する＝仮枠は動かさない）。**よーんが画面で編集した下書きは上書きされない**（画面の編集が正）。**「投稿予約」を押して予約済み（queued）・投稿済みになったら、ファイルを変えても反映されない**（修正は画面から行う）。**1 ネタにつき予約ファイルは 1 つ**（新しい uid のファイルを増やさない）。本文は STEP 5.7 の確定ゲートを通してから書く。

1. トピック要約を決める（投稿文の核心キーワードを名詞句で **10〜15 字**。例:「火星の氷底湖 再検証で揺らぐ」）。初回だけ `uid` を生成（`python3 -c "import uuid;print(uuid.uuid4().hex)"`）、JST 日時は `TZ=Asia/Tokyo date '+%Y%m%d_%H%M%S'`。
2. 予約ファイルを `outputs/scheduled-posts/z01/<YYYYMMDD_HHMMSS>_<topicスラッグ>.md` に Write する（Naming のフォーマット）。**`## 投稿文` に STEP 5.7 を通した確定稿だけ**を入れる。`## セルフリプ` は無ければ「なし」。`## 記録` にソース・フォーカス候補・冒頭フック候補・チェック証跡を**全部**書く（証跡は実起動した各 `/check-*` の結果）。
3. **フック型を記録する**。採用した型（`hook-patterns.md` の①〜⑤。複合の場合は主たる型を1つ）を、`logs/hook_records.csv` に1行追記する：

```bash
REPO=$(git rev-parse --show-toplevel)
echo "$(TZ=Asia/Tokyo date +%F),z01,{①〜⑤+短縮名 例:⑤口火},{投稿文の冒頭15字},{ソースシート}[{ネタ番号}],,{謎},{自分事}" >> "$REPO/logs/hook_records.csv"
```

   - 冒頭15字は投稿文の先頭15文字そのまま（週次振り返りが X投稿一覧の本文と突合するキー。半角カンマは含めない）。
   - **謎**: 答えを知りたくなる問いが立っているかの制作時自己申告。「あり・{問いを一言 例:どうやって出し抜いた？}」または「なし」。**自分事**: 読者の生活・体・誰でも知っているものへの接続の有無。「あり・{接点を一言 例:夜空を見るたび思い出せる}」または「なし」。どちらも半角カンマは含めない（2026-09-21 追加。フック型ラベルだけでは伸びを説明できないため、週次振り返りの検証軸として制作時に宣言する）。
4. **commit & push**：予約ファイルと `logs/hook_records.csv` を master へ（`git add outputs/scheduled-posts/z01/<file> logs/hook_records.csv && git commit && git push`、または `commit_and_sync.sh`）。**push しないと実行環境の破棄とともに記録・予約が消える**（VPS のインポーターは master から `git pull` で取り込む）。リモート環境で git push が認証エラー／非 fast-forward の場合は `git fetch origin master` → origin/master に乗せ直して push、または GitHub MCP で master へ push する。
5. 本文の修正指示が後から来たら、**同じ予約ファイル（同じ uid）を上書き更新**して再度 commit & push する（2 回目の `uid` を発行しない）。ただし反映されるのは postcal 上でまだ下書きの間だけ。予約済み・投稿済みのものは `post.usephys.net` の画面で直してもらう（必要なら画面で状態を確認）。
