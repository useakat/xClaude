# Production Spec — X 短文投稿（Z01）

## Media (生成する媒体)
- X 投稿テキスト（**140 字テキストのみ**。画像なし）

## Input (読み込むファイル)
- `../../plan.md`
- `../../brand.md`（共通ブランド定義）
- `plan.md`（本プロジェクトの目的・ターゲット）
- `brand.md`（本プロジェクトの表現ルール）
- Google Sheets SS1（spreadsheetId: `1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM`）の 4 シート — ネタプール
  - `onePointNeta` / `noteNeta` / `newsTopics` / `thoughts`

## Output (保存先)
- **Gmail 下書き**（投稿は行わず、下書きを作成するだけ）。
- ローカル成果物は残さない（一時ファイル `/tmp/xshort_mail.txt` のみ）。

## Format
- **テキスト**: 常体（だ／のだ調）、3 パート構成（フック→核心→締め。`brand.md` 参照）。
- **文字数**: 厳密に **135〜140 字**（改行・空白を含む総文字数）。
- ハッシュタグ・絵文字・CTA・画像なし。

## Naming

### Gmail 下書き
- 件名: `【X短文投稿】{トピック要約 10〜15 字} YYYYMMDD HH:MM:SS`
- 本文フォーマット（`[最終原稿]`〜`[/最終原稿]` と `[投稿文]`〜`[/投稿文]` の両ブロックに**同一の投稿文**を入れる。`[最終原稿]` は `/check-brand` のラベルと揃えた人間可読の確定稿、`[投稿文]` は cron 投稿フローの `extract_tag.py` が抽出する機械処理用。`extract_tag.py` は `投稿文` タグをリテラル固定・非貪欲で抜き出すため `[最終原稿]` を前置しても誤動作しない。候補類はタグの外に置く。**`[最終原稿]` ブロック内に文字列 `[投稿文]`/`[/投稿文]` を絶対に含めない**＝extract の早期クローズを避ける）:

```
ソース: {ソースシート}[{ネタ番号}]

[フォーカス候補]

{/writer-xpost のフォーカス3候補＋「## 決定」}

[/フォーカス候補]

[冒頭フック候補]

{/writer-xpost の冒頭フック候補（hook-patterns.md の全型 × 各型3案を型別見出し付きで全列挙）＋「## 決定」}

[/冒頭フック候補]

[最終原稿]

{生成した投稿文}

[/最終原稿]

[投稿文]

{生成した投稿文}

[/投稿文]
```

## Rules

### 制作フロー（この spec.md を正として実行する。`/writer-xshort` スキルは廃止予定で使わない）

#### STEP 1: ソースシートをランダムに決定
SS1 の 3 シート（`noteNeta` / `newsTopics` / `thoughts`）から、**2:2:1 の重み付きで 1 シートをランダムに選ぶ**（`onePointNeta` は選定対象外）：

```bash
python3 -c "import random; print(random.choices(['noteNeta','newsTopics','thoughts'], weights=[2,2,1])[0])"
```

- `onePointNeta` を除外し、物語型（noteNeta）・ニュース（newsTopics）・思想（thoughts）を 2:2:1 の割合で出す方針。先にシートを重み付きで選ぶことで、行数の多いシートへの偏りを避けつつ狙った配分にする。
- 選んだシート名を **【ソースシート】** として記憶する。

#### STEP 2: 選んだシートからランダムに 1 行を取得
1. 選んだシートのデータを取得する。範囲は次のとおり：

   | シート       | 取得範囲          | ID/No 列 | 使用する内容列                      | フィルタ列（ステータス／短文最終使用日） |
   |-------------|-------------------|----------|--------------------------------------|------------------------------------------|
   | noteNeta     | `noteNeta!A:N`     | A(No)    | B(タイトル案), E(危機の内容)        | L(ステータス) / N(短文最終使用日)         |
   | newsTopics   | `newsTopics!A:I`   | A(No)    | C(タイトル), D(概要), E(ポイント)   | G(ステータス) / I(短文最終使用日)         |
   | thoughts     | `thoughts!A:C`     | A(ID)    | B(内容)                             | なし（フィルタ対象外）                    |

   ```
   sheets_get_values(spreadsheetId="1zCT0Kv0Q0qr83c6e_jQxUJeUQ1Y8iz0Zlm_0U5RMaEM", range="{選んだシートの取得範囲}")
   ```

2. **候補行の絞り込み**（noteNeta / newsTopics のみ。thoughts はフィルタなしで全行が候補）：
   - ヘッダー行を除いた全データ行のうち、次の条件を**両方満たす行**を候補とする：
     1. フィルタ列の「ステータス」が **「ボツ」ではない**
     2. フィルタ列の「短文最終使用日」が **空、または今日から 90 日以上前**（例: `python3 -c "from datetime import date, timedelta; print((date.today()-timedelta(days=90)).isoformat())"` で閾値日付を求め、文字列比較する）
   - **候補が 0 件の場合はネタ枯渇とみなす**。投稿文生成以降には進まず、STEP 7 で完了報告の代わりに枯渇報告を出して終了する（詳細は STEP 7 参照）。3 段階フォールバックなどは行わない。

3. 候補行の中から **ランダムに 1 行**を選ぶ：

   ```bash
   python3 -c "import random, sys; n=int(sys.argv[1]); print(random.randint(0, n-1))" {候補行数}
   ```

4. 選んだ行について以下を記憶する：
   - **【ネタ番号】**: 選択行の A 列値（No または ID）
   - **【ネタ内容】**: 選択行の主要テキスト（上表の「使用する内容列」を結合）

#### STEP 3: 投稿文生成（`/writer-xpost` を使う）
投稿文の作成は `/writer-xpost` スキルに委ねる。**呼び出す前に `../../style/z01-phrasebook.md`（語彙の好み帳）を Read し、生成時に「好みの方向」に寄せ「避ける」列の表現を出さないようにする。** STEP 2 で選んだネタをテーマとして、文字数範囲 135〜140 字を指定して呼び出す：

```
/writer-xpost
テーマ: {STEP 2 の【ネタ内容】}
文字数: 135〜140字
```

- `/writer-xpost` は本作業フォルダ（z01）の `spec.md`・`plan.md`・`brand.md` を読み込み、投稿文を作成する。
- `/writer-xpost` の出力（フォーカス候補・冒頭フック候補・投稿内容）のうち、**投稿内容** を投稿文として採用する。本フローでは draft への保存は不要（Gmail 下書きが成果物のため、保存はスキップしてよい）。

#### STEP 3.5: セルフ推敲（ファクトチェック前に必ず通す）
STEP 3 で採用した投稿文を、外部チェックに出す前に自分で推敲する：

1. **物語チェック**: `../../style/story-check.md` の7項目（時系列・行動とテーマの整合・接続詞の受け先・史実帰属・結末の完結・フックの回収・語の重複）を1つずつ点検し、該当箇所があれば書き直す。
2. **語彙チェック**: `../../style/z01-phrasebook.md` の「避ける」列に該当する表現が残っていないか点検し、あれば「好みの方向」に置き換える。
3. **字数再計測**: 1〜2 で修正したら実文字数を数え直し、135〜140 字に収まっていることを確認する（`python3 -c "print(len('''…'''))"`）。範囲外なら `brand.md` の削る対象優先度に従って収め直す。

通過後に STEP 3.7 へ進む。

#### STEP 3.7: 素朴な読者チェック（`/check-reader` を使う）
セルフ推敲を通過した投稿文を、制作文脈を知らない読者役エージェントに読ませ、読者の即時疑問を潰す：

```
/check-reader plan.md {STEP 3.5 通過後の投稿文}
```

- 読者役（PE01）が原稿だけを初見で読み、「何の？」「どうやって？」「なぜ？」の疑問・誤解した映像・フック未回収を列挙する。writer は疑問に**本文中で答える形**で改稿し、疑問が出なくなるまで最大3ループ回す（詳細は `/check-reader` スキル参照）。
- 改稿で字数が 135〜140 字から外れた場合は範囲内に収め直す。
- 由来: 2026-08-06 のテミス/アルテミス制作で、/check-fact・/check-brand を1発合格した原稿に読者視点の指摘だけで8往復の推敲が必要だった（「何の影？」「月面に置いたように読める」等）。書き手には見えない疑問を別コンテキストの読者役で検出する。

通過後に STEP 4 へ進む。

#### STEP 4: ファクトチェック（`/check-fact` を使う）
採用した投稿文を `/check-fact` でファクトチェックする（テキスト入力モード）：

```
/check-fact {STEP 3 で採用した投稿文}
```

- 明確な事実誤り（数値・固有名詞・年代・因果の誤り）があれば訂正を反映する。
- 訂正で字数が 135〜140 字から外れた場合は、`brand.md` の削る対象優先度に従って範囲内に収め直す。
- **一次情報主義**：距離・サイズ・年代などの数値は、プレス記事・二次情報の丸め値で確定しない。一次情報（論文・arXiv・公式）に遡り、赤方偏移からの距離のような換算が必要な値は計算して裏取りする（例: z→ルックバック/共動距離、Mpc→光年）。プレスの「about a billion light-years」等はオーダーを外すことがある。
- **編集後の再チェック**：`/check-fact` 通過後に**数値・固有名詞を1つでも追加・変更したら、その原稿で `/check-fact` を必ず再実行する**（チェックの網の外で新しい数値が混入する事故を防ぐ）。

通過後に STEP 4.5 へ進む。

#### STEP 4.5: 知識ある読者チェック（`/check-critic` を使う）
ファクトチェック済みの投稿文を、知識ある読者役エージェントに読ませ、突っ込みどころを検出する：

```
/check-critic --field {分野} {STEP 4 通過後の投稿文}
```

- 知識ある読者役が、事実への反論・単純化しすぎ・**本文が触れていない前提への疑問**・論理の穴を列挙する（詳細は `/check-critic` スキル参照）。
- **各指摘は一次情報（WebSearch / WebFetch）で裏取りしてから扱う**（指摘自体が誤っていることもある）。事実誤りは修正、本文を強める論点は135〜140字を壊さない範囲で反映、入れない論点は破棄してよい。
- 修正で数値・固有名詞が変わったら STEP 4 の再チェックルールに従う。

通過後に STEP 5 へ進む。

#### STEP 5: ブランド適合チェック（`/check-brand` を使う）
ファクトチェック済みの投稿文を `/check-brand` でブランド適合チェックする：

```
/check-brand brand.md {ファクトチェック済みの投稿文}
```

- `brand.md` の採点基準で全項目が基準を満たすまで該当箇所を書き直す（採点ループ）。最後にトンマナ調整する。
- 採点には**項目2（専門用語・固有名詞の言い換え）**と**項目5（読みやすさ）**を含める。裸の固有名詞（カタログ名・装置型番・専門単位）が残っていないか、「の」3連・無読点35字超・修飾の入れ子2段超の読みにくい一文がないかを機械シグナルで点検し、該当箇所を直す。
- 事実は変えない。字数 135〜140 字を維持する。

#### STEP 5.5: よーん役最終検品（`/check-yohn` を使う）
ブランド適合チェック済みの投稿文を、よーん本人の過去の修正指摘から蒸留した検品ペルソナに読ませる：

```
/check-yohn {STEP 5 通過後の投稿文}
```

- ペルソナは共通コア＋`persona-yohn_z01.md`（主張の強さと証拠の釣り合い・スコープの限定・時点の明示・語の被りに特に厳しい）。指摘が出なくなるまで改稿する（最大3ループ）。字数 135〜140 字を維持し、数値・固有名詞が変わったら STEP 4 の再チェックルールに従う。
- **Z01 は無人フローなので、未収束でもここで止めない**。残った指摘は STEP 7 の完了報告に「未解消の指摘」として添えて Gmail 下書きまで進む。
- 下書き作成後にユーザーから修正指摘が出たら、それは check-yohn の見逃しなので `persona-yohn_z01.md`（媒体を問わない癖なら共通コア）に実例として追記する（自己改善ループ）。

通過後に STEP 6 へ進む。

#### STEP 6: Gmail 下書き作成
**下書き作成は1投稿（このフローで選んだ1ネタ）につき1回だけ。** 作成後に本文修正の指示があっても、新規下書きの作成・旧下書きの削除（作り直し）は行わない（修正版はチャットで提示するに留める）。

1. フォーカス候補、冒頭フック候補、`[最終原稿]` ブロック、`[投稿文]` ブロックを `/tmp/xshort_mail.txt` に Write する（Naming の本文フォーマット）。`[最終原稿]` と `[投稿文]` の両ブロックには**同一の投稿文**を入れる。
2. 件名用トピック要約を生成する（投稿文の核心キーワードを名詞句で **10〜15 字以内**。例:「スマホGPS 相対性理論」）。
3. JST 日時を取得する: `TZ=Asia/Tokyo date '+%Y%m%d %H:%M:%S'`
4. Gmail 下書きを作成する:

```bash
bash scripts/create_gmail_draft.sh \
  --to useakat@gmail.com \
  --subject "【X短文投稿】{トピック要約} {YYYYMMDD HH:MM:SS}" \
  --body-file /tmp/xshort_mail.txt
```

成功判定は `✓ 下書き作成完了` の出力で行う。

#### STEP 7: 完了報告
以下を出力して終了する:

```
✅ ネタ選択完了（ソース: {ソースシート}[{ネタ番号}] / {ネタ概要30字以内}）
✅ 投稿文生成完了（{実文字数}字）
✅ Gmail 下書き作成完了（件名: 【X短文投稿】{トピック要約} {YYYYMMDD HH:MM:SS}）

---
【生成した投稿文】

{投稿文本文}
```

**STEP 2 で候補が 0 件だった場合**（ネタ枯渇）は、STEP 3 以降を実行せず、代わりに以下を出力して終了する:

```
⚠️ ネタ枯渇（ソース: {ソースシート} / 候補0件）
{ソースシート}にステータス≠ボツかつ短文最終使用日が空または90日以上前の行がありません。
Gmail 下書きは作成していません。
```

### その他
- **投稿は一切行わない。Gmail 下書きを作成するだけ。**（X 投稿は cron 定時実行のみ）
- **下書きは1投稿につき1回だけ作成する。** 下書き作成後に本文を修正した場合、修正版は**チャットで提示するだけ**にとどめ、Gmail 下書きは作り直さない（`create_gmail_draft.sh` は更新不可で、作り直すと churn・取り違えの原因になるため）。下書き前に本文を確定させること（STEP 4 / STEP 5 通過後の確定稿で STEP 6 に進む）。
- 画像は生成・添付しない（テキストのみ）。
- **記号のような固有名詞・専門語は「イメージのわく表現」に置き換える**（`brand.md`「専門語・固有名詞の言い換え（徹底）」参照）。カタログ名・観測装置の型番・赤方偏移などを本文に裸で出さない（例: 銀河J1007+3540 →「約19億光年かなたの銀河」）。ただし探査機・宇宙船・人物など物語の主人公となる固有名詞は例外で、そのまま使い初出時に一言補足する。
- **数値は一次情報で確定し、チェック後の編集で数値・固有名詞を足したら `/check-fact` を再実行する**（上記 STEP 4 の一次情報主義・再チェックを本文修正フェーズでも守る）。
- **読みにくい一文を残さない**：各文を「の」名詞連鎖3回以上・読点なし35字超・修飾の入れ子2段超で点検し、該当したら語順を「場所→対象→動詞」に整理して一文一義に割る。
- ネタ選定は noteNeta / newsTopics のみステータス（≠ボツ）と短文最終使用日（空または90日以上前）でフィルタする。thoughts はフィルタなし（高頻度運用のため在庫を絞らない）。候補が0件になった場合はネタ枯渇として下書きを作らず終了する（フォールバックで条件を緩めない）。
- 短文最終使用日への書き込みは本フロー（下書き作成時）では行わない。**実際に X 投稿された時点**で `scripts/post_from_email.sh` → `scripts/record_output.py` が SS1 の該当行に記録する（下書きが破棄・未投稿のまま終わった場合はネタが消費扱いにならない）。
- 反応の良かったネタは plan.md の方針に従い W001 / W002 / W003 へ昇格候補とする（昇格判断は本フロー外で実施）。

## Verification
- テキスト字数が **135〜140 字**に収まっている（`python3 -c "print(len('''…'''))"` で確認）。
- `/check-reader` を通過している（読者の即時疑問・誤解した映像・フック未回収が解消済み）。
- `/check-fact` を通過している（事実誤りが訂正済み）。
- `/check-critic` を通過している（知識ある読者の指摘を一次情報で裏取りし、事実誤りが修正済み）。
- `/check-brand` のブランド適合チェックを通過している（採点基準を満たす）。
- `/check-yohn`（よーん役最終検品）を通過している（未収束の指摘があれば STEP 7 の完了報告に注記済み）。
- `brand.md`（Writing Rules / Do Not）と矛盾しない。
- 本文にカタログ名・観測装置の型番・赤方偏移など記号のような固有名詞が裸で残っていない（距離・大きさ等に言い換え／補足済み）。物語の主人公となる固有名詞（探査機・人物名等）は初出時の一言補足付きなら使用可。
- **ストーリー型（noteNeta / thoughts）・ニュース型（newsTopics）の場合、本文に「いつ（年）」と「誰が（NASA 等の実施主体、または人物・探査機・衛星などの主人公）」が書かれている。**
- 距離・サイズ・年代の数値が一次情報（論文・公式）で裏取りされている（プレスの丸め値のまま出していない）。`/check-fact` 通過後に数値・固有名詞を編集した場合は再チェック済み。
- 読みにくい一文がない（「の」名詞連鎖3回以上・読点なし35字超・修飾の入れ子2段超に該当する文がない）。
- `plan.md` の目的（反応観測・高頻度・テキストのみ）に沿う。
- Gmail 下書きの本文に `[最終原稿]`〜`[/最終原稿]` と `[投稿文]`〜`[/投稿文]` の両ブロックが存在し、開き・閉じタグで囲まれ、両ブロックの投稿文が同一である。
- `[最終原稿]` ブロック内に文字列 `[投稿文]`/`[/投稿文]` が含まれていない（extract_tag.py の早期クローズ防止）。
- 下書き作成後に本文修正が入っても、新たな下書きが作成されていない（1投稿1下書き）。
- ハッシュタグ・絵文字・CTA・画像が含まれていない。
- noteNeta / newsTopics 選定時、候補行がステータス≠ボツかつ短文最終使用日が空または90日以上前の条件を満たしている（候補0件の場合は下書きを作らずネタ枯渇報告で終了している）。
