モード判定後の工程（本文作成・各種チェック・画像・セルフリプ・保存）は各モード共通。分岐は「題材の確定」までに閉じる。

## Output (保存先)

- 添付画像: `output/thumbnail.png`


## Format

公開原稿 `output/index.md` には、以下を明示して1ファイルにまとめる：

```
# [タイトル/識別用の短い1行]

## 本編
[投稿本文。X内で完結。末尾にハッシュタグ]

## セルフリプ
note を読みたくなる導入1文と [note URL]
```

- 本編とセルフリプは別投稿として送る前提で、見出しで明確に分ける。
- note URL が未確定の段階では `[note URL]` のままにし、公開時に差し替える。


## Rules

### 制作フロー

1. **モード判定（冒頭で確認）**: ユーザーに「モードA: `noteNeta` から選ぶ／モードB: 既存 note 記事から／モードC: 分割設計ブリーフ `funnel-brief.md` から」のいずれかを確認する。**回答を待ってから次へ進む。**
2. **題材の確定（モードで分岐）**

   - **モードB**: note 記事のプロジェクトフォルダをユーザーに尋ねる。ユーザーは**正確なフォルダ名とは限らず、フォルダ名に含まれる単語だけを指定することもある**。`../../w002/` 配下のフォルダ名を対象に、指定語を含むフォルダを探す。
     - 1件だけ一致 → そのフォルダを採用する。
     - 複数一致 → 候補をユーザーに提示して1つ選んでもらう（**回答を待つ**）。
     - 一致なし → `../../w002/` のフォルダ一覧を提示して選び直してもらう。
     確定したフォルダの `output/index.md`（題材の正本）を読み、物語の核と、人物名・日付・装置の帰属・呼称を確定する。**ここに無い事実を新たに作らない。**
     続けて販促の準備を行う：
     - **note 公開 URL の取得**: 「note投稿一覧」シート（SS3, `note投稿一覧!B:C`）から記事タイトルでマッチして B列の URL を控える。見つからなければユーザーに確認する（**回答を待つ**）。
     - **売りの温存**: 同フォルダに `draft/funnel-brief.md` があれば **`## note の売り（有料の引き）` だけ**を読み「本編に書かない核」を確定する（X長文の範囲・セルフリプ文面は流用しない）。無ければ記事正本から課金壁以降の核心・payoff を特定する。いずれも本編に書き切らない。
     - **過去の販促投稿の確認（重複回避）**: `outputs` シート（SS2, `outputs!A:H`）で F列＝控えた note_url の W001 行を検索し、B列の投稿URLの tweet ID で「X投稿一覧」（SS3, `X投稿一覧!B:C`）から過去の販促本文を取得して読む。**【過去フォーカス】**（過去に使った場面・切り口・フック型）を記憶する。過去投稿が無ければスキップ。
   - **モードC**: 分割設計ブリーフ `funnel-brief.md`（通常 `../../w002/<指定フォルダ>/draft/funnel-brief.md`）を特定して読む（曖昧なら確認）。**題材＝ブリーフの `## X長文の範囲`**（到達点・あえて出さない核）を正とし、この範囲で約600字・X内完結の物語にする。人物名・日付・装置の帰属は notebook（不足時は同フォルダの note `output/index.md`）で確定し、**ここに無い事実を作らない**。ブリーフの `## セルフリプ` 確定文面と `notebook_id` を控える。
3. **投稿フォルダ作成（各モード共通）**: `projects/w001/YYYYMMDD_[topic]/` を作成し、`draft/`・`output/` を用意する。`[topic]` はモードAなら【選定ネタ】、モードB/Cなら note 記事／ブリーフのタイトルから短く付ける。**モードC** では、起点にしたブリーフの相対パス（例 `../../w002/2026-06-19_ボイジャー再点火/draft/funnel-brief.md`）を `{投稿フォルダ}/funnel-brief-ref.md` に1行で記録する（導線の来歴記録）。
4. **notebook の準備（モードで分岐）**: 本文作成・ファクトチェックは、ここで用意する notebook のソースだけを根拠にする。
   - **モードA**: `/research_setup-sources` を【選定ネタ】のテーマ（タイトル案／主人公(ミッション名)）で実行し、NotebookLM の notebook を作成、Deep Research で信頼できるソースを収集・追加する。返ってきた notebook_id を控える。
   - **モードB**: `../../w002/<指定フォルダ>/notebook-id.md` を読み、その notebook_id を再利用する（note 記事執筆時に作成済みの notebook）。**w002 フォルダや notebook-id.md が無い古い記事の場合は、`/check-fact` にフォールバックせず、その場で用意する**：①w002 フォルダが無ければ遡及作成（`projects/w002/<公開日>_<スラグ>/` に記事本文を `output/index.md` として保存）、②`/research_setup-sources` を記事のテーマで実行して notebook を新規作成し、notebook_id を **w002 側の** `notebook-id.md` に保存する（次回販促・記事再検証で再利用するため。w001 投稿フォルダだけに置くと次回見つからない）。初稿を書く**前**にこれを済ませ、一次ソースを土台にする。
   - **モードC**: `funnel-brief.md` の `notebook_id`（＝W002 と共有）を再利用する。
   - いずれのモードも、使う notebook_id を `{投稿フォルダ}/notebook-id.md` に1行で保存する。
5. **本文作成（フォーカス→冒頭フック→本文の3段階対話制作）**: `/writer-xstory` に従う。**notebook のソースに無い事実は創作しない**（縛りはステップ6 の `/check-fact-lim` で担保）。
   - **モードA → 状況A（テーマ先行）**: 引数として【選定ネタ】の情報を渡す。フォーカスは「どの切り口を主役にするか」から3候補→相談で決定。
   - **モードB → 状況B（note記事あり）**: 正本＝確定した `../../w002/<指定フォルダ>/output/index.md`。フォーカスは記事の「最も引きの強い一場面」から3候補→相談で決定。**フォーカス3候補は【過去フォーカス】と異なる場面・切り口から出す**（過去と同じフォーカス・同型フックは候補から除外）。「売りの温存」で確定した核は本編に書かない。
   - 共通: 冒頭フックは5型×3=15案→相談で決定、決定フックに続けて本文を作成する。中間生成物は `draft/focus-candidates.md`・`draft/hook-candidates.md`・`draft/draft.md` に残る。**本文の保存先は `draft/draft.md`。**
5.5. **折り返しブロックの設計（本文執筆の前に確定させる）**: 約600字の本編はタイムラインで**先頭 280 weight**（全角=2/半角=1。日本語だけなら140字）までしか表示されず、残りは「さらに表示」に畳まれる。読者が最初に見るのはこの可視ブロックだけなので、**本文を書き切ってから切れ目を確認するのではなく、可視ブロックを先に固定してから残りを書く**。
   - 決定したフックに続けて、**280 weight 以内に収まる冒頭ブロック**を先に書き切る。境界は目視で数えず `python3 ../../scripts/x_fold_split.py <本文ファイル>` で確認する。
   - **切れ位置が謎・宣言・数字の直後に来るようにする。** 語の途中・説明の途中で切れる配置にしない。
   - 可視ブロックの中で**答えを出し切らない**。読者が「答えを知りたい」と思う問いを1つ以上残し、その答えは折り返しの向こうに置く。
   - 確定した可視ブロックと、そこで伏せている情報を `draft/hook-candidates.md` の末尾に「## 折り返しブロック」として記録する。
6. **ファクトチェック（初回・ユーザー提示前）**: 本文ドラフトができたら、**ユーザーに見せる前に** `/check-fact-lim <notebook_id> {本文}`（`{投稿フォルダ}/notebook-id.md` の ID を使用、notebook ソース限定、最大5回ループ）を**1回**実行し、**明確な事実誤りを反映**する（ステップ4で notebook を必ず用意するため `/check-fact` フォールバックは廃止）。
   - **注記**: 修正案を書くのは `check-fact-lim`（Claude）であり、NotebookLM は事実の照合先にすぎない。`check-fact-lim` の**「完全性チェック」由来の技術ディテール追加は、W001 の叙情トーンと約600字を壊さない範囲で取捨選択する**。**事実誤りの訂正は必ず反映**。字数超過時は本筋に不要な技術描写から削る。
6.3. **素朴な読者チェック（ユーザー提示前）**: `/check-reader plan.md {本文}` を実行する。読者役（W001 persona）が初見で読み、「何の？」「どうやって？」の疑問・誤解した映像・フック未回収を列挙する。疑問に本文中で答える形で改稿し、疑問が出なくなるまで最大3ループ。
6.4. **折り返しチェック（ユーザー提示前）**: `/check-reader --fold plan.md {本文}` を実行する。読者役（W001 persona）がタイムラインで実際に見える冒頭280weight分だけを読み、「さらに表示」を押すか通り過ぎるかを判定する。判定が「通り過ぎる」または引きの強さが7以下なら**可視ブロックの終わり方**を書き直し、**最大3ループ**回す。事実は変えず、字数（500〜700字）は維持する。3ループで基準に届かない場合は警告をユーザー提示時に添える。
6.6. **知識ある読者チェック（ユーザー提示前）**: `/check-critic --field {分野} {本文}` を実行する。知識ある読者役が、事実への反論・単純化しすぎ・**本文が触れていない前提への疑問**・論理の穴を列挙する。**各指摘を notebook（`/check-fact-lim` への照会）で裏取り**し、事実誤りは修正、本文を強める論点は字数・トーンを壊さない範囲で反映、入れない論点はセルフリプ・note 追記候補としてユーザー提示時に添える。指摘を裏取りなしで反映しない。
7. **ユーザー確認・承認**: 上記チェックを反映した本文をユーザーに提示し、修正・承認を得る。**回答を待ってから次へ進む。**
8. **再ファクトチェック（必要時）**: ユーザーの修正で**事実に関わる変更**が入った場合のみ、`/check-fact-lim` を再実行して反映する。
9. **ブランド適合チェック**: `/check-brand brand.md {本文}` を実行する。`brand.md` の `## 採点基準` で全項目8点以上になるまで該当箇所を書き直し（採点ループ・最大5回）、合格本文をトンマナ調整する。事実は変えない。
10. **添付画像**:  `thumbnail/` の `plan.md`／`brand.md`／`design-brief.md`／`nanobanana-prompt.md` に沿って添付画像を用意する。画像生成自体は外部（nano banana）で行い、`output/thumbnail.png` として保存する。
11. **セルフリプ作成**: note 導線を本編から分離し、別投稿として作る。セルフリプには、note を読みたくなる導入1文と note記事への URL を書く。
    - **モードB**: 毎回新規に作る。導入1文は**今回の本編のフォーカスに合わせ**、過去の販促投稿のセルフリプと文面を変える。`[note URL]` は手順2で取得した実URLを入れる。
    - **モードC**: 新規に作らず、`funnel-brief.md` の `## セルフリプ` 確定文面を使う。`[note URL]` は **note 公開後の実 URL に差し替える**（未公開なら `[note URL]` のまま残す）。
12. **保存**: 本編・セルフリプ・ハッシュタグを `output/index.md` に保存する。
13. **ネタのステータス更新（モードAのみ）**: 使用した【選定ネタ】の L列を「使用済み」に更新する（`sheets_update_values`、対象は【行番号】の L列）。
14. **X投稿用メール下書き作成**: 確定した本編と添付画像を、**X長文投稿の cron が拾える体裁**で Gmail 下書きにする。cron は `scripts/post_from_email.sh`（`scripts/run_xlong_post.sh` 経由）が、件名キーワード `【X長文】` で未処理メールを検索し、本文の `[投稿文]…[/投稿文]` を投稿文として、添付画像（PNG）を画像として X に投稿し、`[リプ]…[/リプ]` があれば**本体投稿直後にセルフリプとして自動投稿**、`[note_url]…[/note_url]` の URL は outputs シート F列（note_url）に記録する仕組み（体裁は `/draft_xstory` STEP 6 に準拠）。
    - まず本文を一時ファイルに書き出す（`[投稿文]` には **本編＝`output/index.md` の「## 本編」（末尾ハッシュタグ込み）** を入れる）：
      ```
      [note_url]
      （該当 note 記事の公開URL。モードAで未作成なら空欄）
      [/note_url]

      [投稿文]
      （本編。末尾ハッシュタグ込み）
      [/投稿文]

      [リプ]
      （セルフリプ文面。note URL 込み。モードB/C＝URL確定済みは必ず入れる。モードA＝未確定はこのブロックごと省略）
      [/リプ]
      ```
    - `scripts/create_gmail_draft.sh`（gws CLI・添付対応）で下書きを作成する。サムネは `--attach` で必ず添付される。**gws の `--attach` はカレントディレクトリ内のファイルしか受け付けない**ため、**投稿フォルダに `cd` してから相対パスで渡す**：
      ```bash
      cd {投稿フォルダ}
      bash $(git rev-parse --show-toplevel)/scripts/create_gmail_draft.sh \
        --to useakat@gmail.com \
      ```
