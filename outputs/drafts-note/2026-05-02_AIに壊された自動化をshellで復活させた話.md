# AIに壊された自動化を、shellで復活させた話

毎朝 6:00、宇宙の話をXに自動投稿する仕組みを動かしている。

作った原稿をGmailに送る。0時過ぎに届く。そして 6:00 になると、cronがメールを読んでXに投稿する。完全自動。

のはずだった。

## 「投稿対象なし」という嘘

ログを見ると、毎朝こう書かれていた。

```
投稿対象メールなし。ループ終了
```

おかしい。Gmailを直接検索してみた。ある。投稿したい文章も入っている。`[投稿文]` タグも正しい。

なのにcronは毎朝「何もありません」と言って終わっていた。

---

## 犯人はスクリプトの中にいた

cronが呼び出していたのは `post_from_email.sh` というシェルスクリプト。その中身を開いて、少し驚いた。

```bash
/usr/bin/claude -p "
以下の手順をループで実行してください...
```

**Claudeが、Claudeの投稿を処理していた。**

cronが起動 → `claude -p`（Claude CodeのCLI）が起動 → Claudeが「Gmailを検索して投稿して」と判断して実行する。LLM（大規模言語モデル）が、毎朝の定刻タスクのオーケストレーターを担っていた。

---

## LLMは、決定的でない

ここが問題の核心だ。

LLMは確率的に動く。同じ入力でも毎回同じ出力を返す保証がない。

Gmailの検索結果はこんなJSONで返ってくる。

```json
{ "threads": [{ "id": "19de08...", ... }] }
```

「threadsがある、処理しよう」と判断するのは簡単に見える。ところがClaudeはたまに、この結果を見て「threads配列が存在しない」と誤判定してループを終了していた。

ログのタイムスタンプも証拠になった。開始と完了が同じ秒。本当にGmailを検索していれば数秒かかるはずなのに。Claudeは検索を実行せず、頭の中だけで「なにもない」と結論を出していた可能性が高い。

エラーは出ない。ログには「投稿対象なし」と書かれるだけ。

**サイレント失敗。最も厄介な種類のバグだ。**

---

## 全部、shellに書き直した

解決策は明快だった。LLMに判断させるのをやめる。

Gmail検索 → スレッドID取得 → 本文取得 → タグ抽出 → 投稿 → ラベル付与。この流れをすべて、bashと既存のPythonスクリプトで実装した。

```bash
THREAD_ID=$(gws gmail users threads list --params "$PARAMS" 2>/dev/null \
  | python3 -c "import json,sys; d=json.load(sys.stdin);
                ts=d.get('threads',[]); print(ts[-1]['id'] if ts else '')")

[ -z "$THREAD_ID" ] && { log "投稿対象メールなし。終了"; break; }
```

これなら確率的ではない。JSONが空ならTHREAD_IDが空文字になり、そうでなければIDが取れる。毎回同じ。

タグ抽出用の小さなヘルパー（`extract_tag.py`）も1枚書いた。`[投稿文]`と`[/投稿文]`の間を正規表現で抜くだけ。30行。

`--dry-run` フラグも仕込んで、本番前に確認できるようにした。dry-runが完璧に通ったのを見てから、本番実行した。

投稿まで **5秒**。従来の `claude -p` 起動とはケタが違う。

---

## LLMを信頼する場所、しない場所

これは単なるデバッグの話ではない。

LLMは、曖昧な状況を判断し、文章を生成し、創造的な問いに答えるのが得意だ。しかしcronのような「毎回同じことを確実に実行する」タスクには向いていない。

人間が一目で分かる「threadsがある」を、LLMは確率的にしか判断できない。その確率が99%でも、毎朝365回動かせば年に数回は失敗する計算になる。

**確実性が求められる場所に、確率的なものを置いてはいけない。**

LLMを使う場所と、shellで書く場所。この境界を、もっと意識的に引く必要がある。

宇宙の話を届ける仕組みが、ようやく確実に動くようになった。
