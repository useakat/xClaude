# check-yohn — よーん役最終検品

## 目的

ユーザー（よーん）に原稿を提示する前に、**よーん本人の過去の修正指摘から蒸留した検品役
エージェント**に原稿を読ませ、「よーんならここを直させる」という指摘を先回りして出し、
writer が反映する。狙いは、フロー11（セクション別確認）でのユーザーとの修正往復を、
本当に新しい判断だけに絞ること。

> 由来: 2026-08-20、W002 の過去セッション履歴（ケプラー K2・オポチュニティ・
> チャンドラセカール）からユーザー発言922件を抽出・分析。オポチュニティ記事だけで
> 修正指摘のべ約90箇所・24往復が発生しており、その大半が繰り返し出る同型の指摘
> （不正確な表現・因果の飛躍・像を結ばない比喩・脇道の固有名・見せ場の熱量不足・
> 文末リズム）だった。同型の再発を提示前に止める。

**既存チェックとの役割分担**（このスキルは置き換えではなく最終ゲート）:

| 工程 | 担当 |
|---|---|
| 素朴な読者の誤解・曖昧・不自然 | `/check-reader` |
| 事実の裏取り | `/check-fact-lim` |
| 知識ある読者の反論 | `/check-critic` |
| ブランド適合 | `/check-brand` |
| **よーん固有の判断の再現（上記の取りこぼし含む）** | **`/check-yohn`（本スキル）** |

**配線位置（各 spec）**: W002 フロー10.5（セクション別確認の直前）／W001 フロー6.8
（ユーザー確認・承認の直前）／W003 フロー6.5（画像生成・最終確定の前）／Z01 STEP 5.5
（Gmail 下書き作成の前。Z01 は無人フローなのでブロックせず完了報告に指摘を残す）。

## 入力の解釈（引数規約）

- **先頭トークンが `.md` で終わるパスなら、それをペルソナ定義ファイルとして扱い、残りを本文とする。**
  省略時は共通コア `.claude/skills/check-yohn/persona-yohn.md` を使う。
- **プロジェクト別補足の自動選択**: 本文の作業フォルダが `projects/w001|w003|z01` 配下なら、
  共通コアに加えて `persona-yohn_<プロジェクト>.md`（例: `persona-yohn_w001.md`）も読み込む。
  w002 は共通コアのみ（コアが w002 コーパス由来のため）。
- 本文がファイルパス（存在する `.md`）で渡されたら Read して本文とする。

## 手順

### STEP 1: 検品材料の確定

以下を Read する:

1. ペルソナ定義 — 共通コア `persona-yohn.md`（判断基準1〜10 と実例）＋該当すれば
   プロジェクト別補足 `persona-yohn_<w001|w003|z01>.md`
2. 対象プロジェクトの `brand.md`（w002 は `projects/w002/brand.md`、w001/w003/z01 も各
   プロジェクト直下）— 成文ルール
3. あれば `draft/agenda.md`（w002）や承認済みのフォーカス・冒頭フック（w001/w003/z01）
   — 構成との食い違い・見せ場の熱量判定に使う。w002 の agenda に「感情の設計図」
   （保留リスト＝物語の疑問と回収章・感情の線・1場面）があれば検品役に渡し、
   **設計どおりの保留を「未回収」として指摘させない**（保留リスト外の理解の疑問は従来どおり）

### STEP 2: 検品役エージェントを起動する

**Task ツール（general-purpose サブエージェント）で検品役を起動する。** プロンプトには
以下を渡す:

1. ペルソナ定義の全文
2. brand.md の Writing Rules・Do Not（成文ルール）
3. agenda.md の構成・見せ場指定（あれば）
4. 原稿本文

検品役への指示テンプレート:

```
あなたは、この原稿の発行者「よーん」本人です。以下のペルソナ定義は、
あなた自身が過去の原稿に出した修正指摘の実例と判断基準です。これを自分の
判断の癖として完全に体現してください。

{persona-yohn.md 全文＋該当プロジェクトの補足ファイル全文}

成文ルール（brand.md 抜粋）:
{Writing Rules / Do Not}

{あれば: 承認済み構成と見せ場 H2 の指定}

以下の原稿を、公開前の最終検品として読み、「自分ならここを直させる」箇所を
すべて列挙してください。褒める必要はありません。指摘ゼロなら「指摘なし」と
だけ返してください。

{原稿本文}

出力形式（よーんの実際の指摘形式を模す）:

【要修正】（修正案まで一意に決まるもの）
* 現行の文 -> 修正案

【違和感】（直すべきだが修正案は writer に委ねるもの）
* 現行の文　　＋なぜ気になるかを一言

【疑義】（事実の確認が必要なもの。修正案は出さない）
* 現行の文　　＋確認したい点を質問形式で
  （例: これはいつの時点の話？／この根拠となる出典は？／◯◯と矛盾しない？）

【構成】（章の目的・統合・約束の回収など、文単位でない指摘）
* 指摘内容

各指摘に、依拠した判断基準の番号（1〜10 または brand.md）を添えてください。
判断基準のどれにも根拠づけられない好みだけの指摘は出さないでください。
```

**制作の経緯・過去の版・チェック履歴は渡さない**（検品役の判断を原稿そのものに向けさせる）。

### STEP 3: writer が指摘に対処する

- 【要修正】【違和感】→ 該当箇所のみ改稿する。**指摘されていない箇所は変えない。**
  像を結ばない表現は、言い換えの前に「無くても文が成立するか」を確かめ、成立するなら削除。
- 【疑義】→ notebook（`notebook-id.md` の ID）または既存出典で裏取りし、
  事実が違えば修正、正しければ本文に前提・時点を一段補う。**裏取りなしで反映しない。**
- 【構成】→ 対処が大改稿（章統合・付録化など）になる場合は、無理に自動反映せず
  「未解消の指摘」としてユーザー提示に回してよい（構成の変更はユーザーの判断）。
- 事実（数値・固有名詞・因果関係）は出典の範囲内でしか変えない。字数制約は維持する。

### STEP 4: 収束ループ

改稿した原稿で STEP 2 を再実行する（検品役は**毎回新しいサブエージェント**で起動する）。

- **終了条件**: 【要修正】【違和感】【疑義】がゼロ（【構成】のユーザー判断行きは残ってよい）
- **最大3ループ**。収束しない場合は残った指摘を「未解消の指摘」として警告付きで出力し、
  提示をブロックしない（判断はユーザーに委ねる）

## 出力形式

```
[最終原稿]

{改稿後の本文}

[/最終原稿]

[よーん役検品サマリー]

| ループ | 要修正 | 違和感 | 疑義 | 構成 | 判定 |
|---|---|---|---|---|---|
| 1回目 | X件 | X件 | X件 | X件 | No |
| 2回目 | … | | | | |

反映した主な指摘:
- {指摘} → {対応}

ユーザー判断に回す指摘（あれば）:
- {構成レベルの指摘}

[/よーん役検品サマリー]
```

未収束の場合は冒頭に警告:

```
⚠️ よーん役の指摘が3ループで収束しませんでした（残: {残った指摘}）
```

## 自己改善ループ（運用ルール）

**check-yohn 通過後の提示でユーザーから新たな修正指摘が出たら、それはこのペルソナの
見逃しである。** 制作が一段落したら、その指摘を実例として追記する — 媒体を問わない癖なら
共通コア `persona-yohn.md` の該当する判断基準へ、そのプロジェクト特有の癖なら
`persona-yohn_<プロジェクト>.md` へ（分類できなければコア末尾の「見逃し追記ログ」へ）。
これによりペルソナは記事を重ねるごとにユーザー本人に近づく。

## 禁止事項

- 検品役に制作の経緯・過去の版・他チェックの履歴を渡さない
- 指摘されていない箇所を writer が「ついでに」直さない
- 【疑義】を裏取りなしで本文に反映しない
- 事実（数値・固有名詞・因果関係）を出典の範囲外に変えない
- このチェックを理由にユーザー提示を止めない（未収束でも警告付きで提示に進む）
