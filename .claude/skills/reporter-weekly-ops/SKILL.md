## 役割分担（他レポートと重複させない）

| スキル | 頻度 | 担当 |
|---|---|---|
| `/reporter-weekly` | 週次 | 数値週報（フォロワー・インプ・やったこと・来週タスク） |
| **本スキル** | 週次 | **運用の振り返り**（プロジェクト別の伸び・沈みの要因分析、運用アクションの決定と消化確認、**note 導線 施策の検証**（レジストリ指定の率指標のみ）） |
| `/reporter-monetization` | 月次 | マネタイズ（売上・CTR/CVR・導線） |

- 売上・CTR/CVR の集計はしない（monetization の領分）。ただし「⑧ note 導線 施策の検証」は、施策レジストリが指定した率指標を `scripts/note_funnel_measures.py` の出力から転記する。月次の売上総括は引き続き monetization。
- フォロワー・週間インプの総括数値は冒頭に1行置くだけに留める（weekly の領分）。
- 本スキルの中心は「**どの投稿が・なぜ伸びた/沈んだか**」と「**来週の運用をどう変えるか**」。

# STEP 1: 対象週の決定

引数があればその週の月曜日（YYYY-MM-DD）として解釈する。なければ**今週（実行日を含む週）の月曜〜日曜**を対象にする。週の途中（日曜以前）に実行した場合は集計が途中経過になるため、レポート冒頭にその旨を1行明記する。

```bash
python3 -c "
from datetime import datetime, timedelta, timezone
import sys
JST = timezone(timedelta(hours=9))
args = sys.argv[1:]
if args:
    base = datetime.strptime(args[0], '%Y-%m-%d').date()
    monday = base - timedelta(days=base.weekday())
else:
    today = datetime.now(JST).date()
    monday = today - timedelta(days=today.weekday())
sunday = monday + timedelta(days=6)
iso_week = monday.isocalendar()[1]
prev_monday = monday - timedelta(days=7)
print(f'monday={monday}')
print(f'sunday={sunday}')
print(f'week_id={monday.year}-W{iso_week:02d}')
print(f'prev_week_id={prev_monday.year}-W{prev_monday.isocalendar()[1]:02d}')
print(f'week_label={monday.strftime(\"%-m月%-d日\")}週')
" -- "$1"
```

各変数を記憶する。

`sheets_get_values(spreadsheetId=SS2, range="outputs!A:H")` を取得し、A列日時が当週（月〜日）の行を抽出する。

- 媒体判定: B列 URL が `threads.com` → threads / `note.com` → note / それ以外 → X

## 2-3. 週間インプ（未記入時は暫定値を自動算出）

`sheets_get_values(spreadsheetId=SS3, range="日次記録!A:AB")` の当週日曜行から `週間インプ` を取得する（冒頭サマリー用・これ以上は使わない）。

- 根拠: 週間インプ＝月〜日の日次インプ合計（2026-10-11 週で 20,771＋3,975＝24,746 の一致を確認。2026-10-18 決定）

## 4-1. プロジェクト別実績（**過去8週ローリング**で集計）

当週だけでなく、**当週を含む過去8週の X 投稿**を outputs から抽出してメトリクスを紐づけ、プロジェクト（what_id）別に整理する：

- 本数・**中央値IMP**・**IQR外れ値除外平均IMP**・最大IMP
  - IQR法: Q1−1.5×IQR 〜 Q3+1.5×IQR の範囲外を外れ値として除外した平均。除外した値はレポートに明記する
  - 中央値=通常運転の1本 / 除外平均=通常期待値 / 最大=バズの有無、の3点で読む
  - **n<4 の行は中央値・除外平均を出さず実値を列挙する**（統計的な見せかけを作らない）
- 当週分は別途、各プロジェクトのトップ投稿とワースト投稿（本文冒頭 40 字で識別）を出す（**z01 は選定対象外**）
- **z01 の位置づけ**: z01 は note ネタの反応観測とアカウント発信力の定点観測が目的で、**改善対象外**。①の実績表・ベースライン監視には載せるが、②の伸び・沈み分析には入れない。フック型の記録など**仮説検証の場**としては使ってよい
- **ベースライン監視**: z01 の週中央値を毎週記録する（毎週コンスタントに本数が出るため、アカウント配信量の温度計として使う。2026年7月中旬の半減をこの指標で検知した実績）
- **W001 の分散記録**: W001 全投稿の実IMPを1本ずつ累積リストに追記する（週2本ペースで n=15〜20 に達したら「長文は他の型より強いか」の統計検証が可能になる。当たり率・外れの下限もこのリストで追う）
- threads は views ベースで別枠（転載は本数のみ）
- note は当週公開記事の有無とタイトルのみ（ビュー詳細は monetization の領分）

**平均単独で判断しない**（少数の跳ねに引きずられるため。2026-08-12 の @galileo_fun 分析、2026-08-16 の8週分析で確認済み）。

# STEP 5: 伸び・沈みの要因分析

**対象は改善対象プロジェクト（W001・W003 など）のみ。z01 は除外する**（改善対象外・定点観測用。STEP 4-1 参照）。

トップ投稿とワースト投稿について、次の観点で要因を分析する（データで確認できることと推測を区別して書く）：

1. **フックの謎の強さ**: 型は `logs/hook_records.csv` の制作時記録を第一に使い（無い投稿のみ自分で型分類し「事後分類」と明記。2026-09-21 以降の記録には `謎`・`自分事` 列＝制作時の自己申告があり、あれば事後推測より優先して使う）、`style/hook-patterns.md` の型分類に加え、**答えを知りたくなる謎が立っているか**を見る（8週分析で桁を変えた主要因。例:「手順を知る者は、もう誰も残っていない」= 22.8万IMP）
2. **折り返し位置**: `python3 scripts/x_fold_split.py` で可視ブロックの切れ方を確認する。**「文末で切れているか」ではなく「答え・種明かしの直前で切れているか」を見る**（語中切断でも答え直前なら伸びた実績あり。同時期内の 2〜5倍差を説明する要因）
3. **題材の型**: 「執念・復活・逆転の物語」か「予告系ニュース・教訓なし雑学」か（8週トップ5は全て前者、ワーストは後者に集中）。読者の体・生活・誰でも知っているものへの接続も見る
4. **時期・アカウント状態**: z01 ベースライン（STEP 4-1）が低い週の沈みを投稿の出来のせいにしない（交絡の分離）
5. **投稿時間帯・曜日**: 当週内で偏りがあるか
6. **前週アクションとの関係**: 前週の「来週の運用アクション」を実施した投稿は成果が出たか

推測には「〜の可能性がある」を付け、断定しない。**要因を1つに決めつけず、データが薄い場合はその旨を書く。**

# STEP 5.5: 仮説の検証

レポートに「検証中の仮説」を引き継ぎ・更新する：

1. 前週レポートの「⑥ 検証中の仮説」を読み、各仮説について当週データで判定を試みる
   - **支持** / **反証** / **判定保留（データ不足）** のいずれかを付ける
   - 判定できた仮説は「検証結果」に移し、結論と根拠データを1〜2行で書く
2. 当週の分析から新たに生まれた仮説を追加する（検証方法と必要データ量も書く）

**時期をまたいで投稿を比較するときは、生IMPを使わない。** アカウントのベースラインは大きく変動する（2026年2〜6月と7〜8月で W001 の IMP 中央値が28分の1に落ちた）。生の数字で比べると、測りたい要因ではなく「投稿時期」を比べることになる。

**ベースライン正規化倍率**を使う：

```
倍率 = 当該投稿の IMP ÷ その投稿より前の「非W001・非リプライ」投稿 直近5本の IMP 中央値
```

- 分母を**非W001**にするのは、W001 側で検証したい要因（字数・フック型など）が分母に混入しないようにするため。分子と分母が独立して初めて、割り算で残るのが検証対象の効果になる
- 分母から**リプライを除く**のは、セルフリプが本体投稿に引きずられて数字が動くため
- 倍率は外れ値に極端に振れる（実績レンジ 1.7〜3974倍）。**平均ではなく必ず中央値**で比較する
- 限界: W001 長文と z01 短文では投稿の性質が違うため「同じ地合いを共有している」という前提は完全ではない。それでも生IMP比較よりは交絡が落ちる


初期仮説（2026-08-16 の8週分析から引き継ぎ）：

- **H1**: W001 長文は他の型より1本あたりの期待値が高い（検証: W001 の n が15〜20 に達したら Mann-Whitney U 検定。現在 n=7）
- **H2**: 折り返し位置を「答えの直前」に設計すると同時期の同型投稿より伸びる（検証: 設計適用済み W001 販促を3本以上積んで適用前と比較）
- **H3**: 7月中旬のベースライン半減は投稿の連続性低下が原因で、毎日投稿＋週2長文で回復する（検証: z01 週中央値が 2,000 台に戻るか、4週観察）
- **H4**: W001 長文は翌日以降もインプを引く尾がある（確定すれば週2本の曜日配置の根拠になる）
  - **検証方法（2026-09-27 設計変更。本記載は 2026-10-11 に同期）**: 旧方式（長文翌日の0本日インプ比較）は「投稿0本日ゼロ」の運用方針と矛盾するため廃止済み。代わりに、日報 routine 相乗りの日次IMPスナップショット（`w001_imp_snapshot.py` → `logs/w001_imp_daily.csv`、稼働中）で W001 の累積IMPを毎日記録し、**投稿2日目以降の日次増分（＝尾そのもの）を直接測る**
  - 判定: W001 のスナップショットが4〜6本たまった時点で、2日目以降増分の合計と初日分の比を本ごとに出し、尾が一貫して残るか（中央値で比較）を判定する。詳細は報告書 `20260927_hypothesis_verification_infra` を参照
- **H5**: 〔**2026-10-18 終了・検証不能**〕W001 は現行の約600字より短い方（500字前後）が伸びる（2026-08-22 追加）
  - 遡及で「短いほど単調に良い」は再現せず（2026-09-21 再計算: 3分割で中間帯が最高）、前向きの帯別交互制作（500字帯/650字帯）は4週経過で各帯 n=1〜2 しか集まらず、帯を狙って書くこと自体が未達要因になったため**実行不能と判断して終了**。500字帯 vs 650字帯の優劣は未決のまま閉じる
  - 確度の高かった部分（本文700字超の弱さ）は **H6 に引き継ぐ**。字数の統一ルール（**本文のみ・ハッシュタグ行/改行/空白を除く**。X投稿一覧の「文字数」列はタグ・改行込みのため使わない）も H6 で継続
- **H6**: W001 は**本文700字超だと700字以下より伸びない**（2026-10-18 追加。H5 の後継）
  - **評価指標**: 生IMPは使わない。ベースライン正規化倍率＝`当該投稿のIMP ÷ その投稿より前の「非W001・非リプライ」直近5本のIMP中央値` の**中央値**で2群比較。あわせて **note リンクCTR** を併記する（削ってIMPが出てもCTRが落ちるなら改定しない。W001 の第一目的は note 流入のため）
  - **判定条件（事前固定）**: 現体制（2026-06-13 以降）のサンプルで Mann-Whitney（片側: 700字以下＞700字超）**p<0.05**。分母の直近5本に IMP 2万超を含む「バズ隣接」投稿を除いた感度分析を併記し、**両方が同方向なら確定**
  - **遡及初回判定（2026-10-18・支持傾向/暫定）**: 現体制で 700字以下 n=11（倍率中央値 7.3）vs 700字超 n=6（中央値 3.0）→ p=0.071。バズ隣接除外では n=7（中央値 15.7）vs n=5（中央値 2.1）→ **p=0.014**。700字超は現体制6本すべて倍率4.4以下（反例ゼロ）。全期間（2/11〜）では p=0.113 だが、2〜5月の高ベースライン期は倍率でも正規化しきれない時代交絡があるため参考値扱い
  - **運用への反映**: 投稿前に本文字数を数え、700字超なら削ってから出す。`projects/w001/brand.md` の字数レンジ（優 560〜640字／合格 500〜700字）は維持

# STEP 5.7: note 導線 施策の検証

施策レジストリ `docs/plans/note_funnel_measures.md` の「実施中」の施策について、当週の数値を出して判定し、レジストリに記録する。数値はスクリプトが出し、判定だけを Claude が行う。

1. 数値を出す（発信記録シートから CSV を書き出すので十数秒〜1 分かかる）：

```bash
python3 $(git -C /root/xClaude rev-parse --show-toplevel)/scripts/note_funnel_measures.py --week [week_start]
```

   - 失敗（exit≠0）してもレポート作成は止めない。⑧ に「未取得（エラー内容）」と書く
   - 詳細（投稿ごとの内訳・週別）が要るときは `--json` を付けて再実行する

2. 「実施中」の各施策について、出力の値をレジストリの「比較方法・判定条件（事前固定）」と照合し、**支持** / **反証** / **保留（データ不足）** のいずれかを決める。根拠は 1〜2 行。条件に満たない n や窓は「保留」にし、数値を推測しない
3. レジストリの該当施策の `#### 判定履歴` 表に 1 行追記する（Edit ツール）：

```
| [week_id] | [値。スクリプトの「表示」列を要約] | 支持/反証/保留 | [根拠 1〜2 行] |
```

   - 同じ `[week_id]` の行が既にあれば上書きし、重複させない
   - 判定が**確定**（支持または反証）したら、その施策の「状態」を「判定済み（支持）」などに変え、順位表の「状態」と「直近判定」も同じ内容に更新する。確定の基準はレジストリの判定条件に従う
5. 同じ出力の末尾「## 価格のはしご」（note 記事の価格設定ルール。`note_price_rule.py` が判定、毎朝 `note_article_daily.py` がメールで通知済み）を ⑨ に転記する。**状態が「未対応」の記事**（通知済みで、価格も改稿日も変わっていない）は ⑨ の先頭に「・未対応: …」として必ず列挙する。未対応が 0 件なら「未対応: なし」。判定も催促もしない（価格と改稿はよーんの判断）
4. 「未着手」の上位施策を ⑤ 来週の運用アクションの候補として 1 行で示す（実施するかはよーんの判断。実施日の記入はよーんが実施したときに行う。ここでは状態を変えない）
